# 重复请求抑制（问两次 / 答两次）· 实施与验收记录

> 触发：用户报告「同一个问题被问两次、回答被回两次」。
> 定案：**A 版（幂等键）+ B 版（响应去重）合并落地为网关侧的「重复请求抑制」**。
> 默认**只观察**，不改变任何响应；拿到重复率再决定是否开启抑制。
>
> 代码落点：`src-tauri/src/proxy/dedup.rs`（判定与状态）、`src-tauri/src/proxy/server.rs` 的 `dispatch`（接线）。
> 行为判据：`src-tauri/tests/dedup.rs`（端到端）与 `src-tauri/src/proxy/dedup.rs` 的 `mod tests`（判定逻辑）。

---

## 一、症状与判据

用户侧看到的：只问了一次，却收到两份回答；同一条弹窗 / tool 调用被执行两次。

**根因不是模型，是「同一个请求被执行了两次」。** 三种触发方式与观测特征：

| 触发方式 | 观测到的间隔 | 客户端表现 |
| --- | --- | --- |
| 客户端超时重试（网关只是在慢慢跑） | 5–20 秒 | 两份**不同**的回答 |
| 自动接续 / 重放整轮 | 秒级到分钟级 | 整轮被重做，弹窗重复 |
| 用户或 UI 重复点击发送 | 毫秒级 | 两条请求同时在飞 |

三种表象不同（「答两次」是前两种，「问两次」是第三种），但判据是同一条：
**同一份请求内容在短窗口内出现了两次**。

## 二、为什么没有走「客户端回传幂等键」

规范做法是客户端带 `X-Request-Id` 回来。这条路在本项目当前的调用方上走不通：

- `src-tauri/src/agent_upstream/plugin.rs` 里的 `request_id` 由**网关自己生成**，
  只用于插件往返配对，不是调用方回传的幂等键；
- 主流 SDK 客户端不保证回传，网关无法据此判定。

所以改用**网关侧派生键**：指纹即键，不依赖任何调用方配合。

**关键约束（本轮踩到并修正的一处设计错误）**：指纹里**不能带会话 ID**。
`src-tauri/src/context/mod.rs` 的 `derive_session_id` 对没有回传 `X-Session-Id` 的客户端
**每次生成随机 ID**（这是有意设计，避免相同首问的独立会话共享上下文）。
把随机值并入指纹 ⇒ 同一次请求的两次投递算出两个不同的键 ⇒ **去重永远不命中**。
代价写在这里：不同会话里逐字节相同的请求会被判成重复；实测这个代价很小 ——
客户端重发同一句话时，上一次的回答已经进了历史，两轮的请求体并不相同。

## 三、判定规则（实现口径）

指纹 = `sha256(client | 请求体规范化 JSON)` 的前 16 字节十六进制，前缀 `dedup-v1` 与缓存键区分。

第一个到达的请求拿到该指纹的专用许可（Owner），后续请求排队等它；Owner 执行完登记结局：

| 情况 | 处置 |
| --- | --- |
| 上一次成功交付过 | **明确拒绝**（HTTP 409 + `X-Dedup: conflict`），不重复执行 |
| 上一次执行失败 | 当作没发生过，照常执行 |
| 上一次的窗口已过期 | 当作新请求执行 |
| 等 Owner 超时（默认 10 秒） | **不报错**，这次自行执行 |

**四条排除规则**（不参与去重的请求）：

| 排除项 | 放开的后果 |
| --- | --- |
| 带 `tools` | 工具调用的正确性依赖当轮上下文，合并会执行过期动作 |
| 多模态（图 / 音 / 视频） | 同样的文字配不同的图是两回事，而图的内容不参与指纹 |
| 请求体序列化失败 | 拿不到稳定指纹，判了也是错的 |
| 开关关闭 / 窗口为 0 | 路径与改动前逐位等价（铁律 2） |

## 四、配置项（`AppConfig.dedup`）

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `mode` | `off` | `off` / `observe`（只计数不改响应）/ `enforce`（判重复则拒绝） |
| `window_secs` | 15 | 判定窗口。**要短**：窗口越大越容易把「用户真的问了两遍」误判成重复 |
| `wait_secs` | 10 | Follower 最多等 Owner 多久；等不到就自己执行 |
| `capacity` | 512 | 条目上限，超限按 `inserted_at` 淘汰最老的 |

**为什么默认 `off` 而不是 `enforce`**：抑制会改变用户可见的行为（本该跑第二次的请求不跑了）。
在拿到真实重复率之前默认开抑制，等于拿用户的账单和行为做实验。
`observe` 只计数、只记日志，一个字节的响应都不动 —— 它给出的重复计数，
正是决定要不要开抑制的前提。

## 五、验收（本机实跑，2026-10-13）

| 验证 | 结果 |
| --- | --- |
| `cargo test --jobs 1`（全量） | **exit 0；63 个 suite，1148 passed / 0 failed / 19 ignored** |
| `cargo test --lib proxy::dedup -- --test-threads=1` | **10 passed / 0 failed** |
| `cargo test --test dedup -- --test-threads=1` | **6 passed / 0 failed**（含 `/gw/stats` 暴露计数一例） |
| `cargo check --lib` | exit 0，零告警 |

端到端用例（`src-tauri/tests/dedup.rs`，真网关 + axum mock 上游 + 真 HTTP）：

| 用例 | 判据 |
| --- | --- |
| 关闭时同一请求发两次会调用上游两次 | 对照组：上游 `calls == 2`，`duplicates == 0` |
| 观察模式下重复被计数但不拦截 | 上游 `calls == 2`、两次都 200，且 `duplicates == 1`（计数真的在动） |
| 抑制模式下第二次被拒绝且上游只调用一次 | 第二次 409 + `X-Dedup: conflict`，**上游 `calls == 1`** |
| 抑制模式下不同请求照常执行 | 对照：不同内容 → 两次 200、`calls == 2`、`duplicates == 0` |
| 抑制模式下带工具的重复请求不参与去重 | `duplicates == 0`，第二次不带冲突标记 |
| 观察模式的重复计数通过 `gw_stats` 可见 | 重复前 `duplicates == 0`、重复后 `== 1`；带 `mode` 与 `window_note` |

**「上游只被调用一次」是唯一骗不了人的判据**：只看响应状态码会被
「网关自己拒绝但上游仍被调用」骗过。对照组同样必须存在 —— 否则
「只调用一次」可能只是因为上游根本没被调用。

单元用例（`src-tauri/src/proxy/dedup.rs` 的 `mod tests`）：关闭时完全不做判定、
观察模式计数但放行、抑制模式重复被拒、上一次失败时照常执行、窗口外不拦、
指纹区分内容与客户端、并发两次投递只执行一次、清空条目后计数保留、
不参与去重的请求不建条目。

## 六、具体做过的修正（保留失败轨迹）

1. **`entry()` API 的语义坑**：首版用 `map.entry(k).or_insert_with(...)` 建条目，
   再在同一函数里用 `get_mut` 判定「这是不是第一次」，实测计数出现
   `count` 从 1 直接跳 2 的现象（6 条单测红）。改为显式
   `contains_key` + `insert`，并由一个 `is_first_touch` 标志传递「本次是不是第一次」，
   10/10 转绿。**教训**：`entry()` 的返回值只能说明「调用时不存在」，
   与「本次调用是不是第一个」在并发下不是同一件事。
2. **失败被误判成「只能拒绝」**：`finish` 只登记成功，最开始把
   `outcome = None` 也归进「无载荷 ⇒ 拒绝」，于是客户端遇到一次上游错误后
   重试永远是 4xx。改为 `None => Take`（照常执行），并单独加了一条回归用例。
3. **指纹并入会话 ID 会让去重永不命中**：见 §二。已从指纹输入里移除会话维度，
   并把理由写进 `FingerprintInput` 的文档注释。

## 七、明确未做的（不要把本节内容说成已交付）

- **未开启抑制**：配置默认 `off`。要真正挡住「答两次」，需要把
  `AppConfig.dedup.mode` 设为 `observe` 先取数，确认重复率后再设为 `enforce`。
- **未做非流式响应复用**：`DedupOutcome` 只记「有没有成功交付过」这一个 bit，
  不缓冲响应体。流式响应无法在流已经开始之后重放，而非流式请求在当前调用方上
  不是重复投递的来源 —— 缓冲带来的体积上限 / 超大响应 / 缓冲失败退回一整套边界，
  换不到当前用得上的能力。
- **未验证真实客户端场景**：本轮只有 mock 上游的端到端证据。
  「网关是不是 DSH 会话重复回答的实际来源」尚未确认 —— 关闭这一格需要真实运行
  一轮 `observe` 模式，取 `duplicates` 计数。
- **界面没有入口**：`/gw/stats`（HTTP）已经暴露 `dedup` 与 `cache` 的进程内计数
  （含 `mode` 与 `window_note`，避免与 24 小时窗口混淆），但**设置页没有开关注释、
  统计页也没有展示这两个块** —— 桌面端走的是 Tauri IPC `stats_overview`
  （`commands.rs` 的 `StatsOverview`），那是另一条数据通路，当前没有带这两个字段。
  也就是说：现在能读数据，但界面上看不到，配置也只能改 `config.toml`。
- **未推送**：本轮改动只在本机提交，未 push、未开 PR、未打包。
