## 0. 一句话定位

在既有「多 Provider 聚合 + 打分排序」之上再加两层：**本地模型**作为一等公民进入候选链，**智能模式**在路由前先给请求定性（简单 / 图像 / 复杂思考），再按定性挑模型；需要事实时由网关**代为联网搜索**并把结果注入上下文。

## 1. 需求与验收口径

| 需求 | 可失败的判据 |
| --- | --- |
| 补充本地模型能力 | 扫描本机运行时并列出已装模型；能力位（vision/tools/thinking）从上游元数据自动映射；可一键登记为 Provider 并进入 `auto` 候选链 |
| 简单任务用 Jev | 分类器输出 `simple` 时，`supports_thinking=true` 的候选被 `intent_fit` 压到 0.30，思考模型不会被选中 |
| 图像识别找多模态 | 请求含图片时，候选链中不含 `supports_vision=false` 的模型；响应头回传 `X-Route-Intent: vision` |
| 复杂任务用思考模型 | 分类器输出 `reasoning` 时，不支持 thinking 的候选被压到 0.45 |
| 可以联网搜索 | 未配置任何 API Key 时，搜索仍能返回结果（免 Key 后端）；配置 Key 后走对应后端；后端全部不可用时返回明确错误而不是静默无搜索 |
| Jev 不可用不能拖垮请求 | 决策端点超时 / 404 / 未装模型时，分类器在超时预算内回落启发式规则，请求照常返回 200 |

**明确不做的事**（避免留白被当成缺陷）：

- 不做「让 Jev 生成提示词文本」。Jev（`/v1/systemone`）只返回结构化决策，不返回自由文本。提示词预优化由独立的轻量改写调用承担，且必须显式开启。
- 不在流式响应已开始输出字节后插入搜索结果。理由见 §5.4。
- 本轮不下载任何模型。Jev 模型由用户在界面自选。

## 2. 背景：Jev 是什么，以及本机 edgeJev 的实测能力边界

[Jev](https://typesafe.ai) 是 TypeSafe 的「快速定型决策」API，本质是 System 1 决策模型：给一段 `state` 和若干具名问题，模型在**一次请求**里把全部问题答完，并附带概率与置信度。协议在 Ollama 自 0.35 起的 [`/v1/systemone`](https://ollama.com/blog/ollama-now-supports-jev-style-decision-models) 上标准化。

本机已部署 **edgeJev**（[yzfly/edgejev](https://github.com/yzfly/edgejev)，Apache-2.0），路径 `C:\Users\Admin\Documents\deepseek-harness\default-workspace\jev\`：

| 项 | 实测值 |
| --- | --- |
| 服务 | `http://127.0.0.1:8009/v1/systemone`（与 Ollama 同协议） |
| 形态 | laya-multilingual 转 ONNX **int8**，319.67 MB，`model_name=rl-agent` |
| 设备 | **CPU**（RTX 5080 未启用） |
| 延迟 | HTTP 端到端三题中位 53.2 ms（每题 17.7 ms） |
| `state` 上限 | `max_len=1024` token |
| 输出 token | **0**（scoring pass，不是生成） |
| 量化副作用 | 动态量化下 batch 会影响结果，logits 漂移 0.58 ⇒ 必须固定一次问一批 |

协议形态：

```json
POST /v1/systemone
{ "model": "rl-agent",
  "state": { "prompt": "…" },
  "questions": { "k": { "type": "choice"|"noul"|"score", "instructions": "…", "criteria": … } } }
```

```json
{ "answers": { "k": { "type": "choice", "choice": "…", "probabilities": {…}, "confidence": 0.52 } },
  "usage": { "input_tokens": 76, "output_tokens": 0 } }
```

### 2.1 实测：它判不了「任务复杂度」

本轮用同一服务跑了三种问法 × 五个样本（`docs/` 里保留了可复现命令）。**三种问法全部失败**：

| 问法 | 简单-改变量名 | 中等-写快排 | 复杂-千万级架构设计 | 复杂-500 白屏定位 | 简单-打招呼 |
| --- | --- | --- | --- | --- | --- |
| A 路由式（最贴近其训练分布） | ✅ lookup | ❌ lookup | ❌ lookup（reason 仅 0.392） | ✅ reason 0.864 | ✅ lookup |
| B 复杂度（选项顺序反转） | ❌ hard | ❌ easy | ❌ easy 0.727 | ❌ hard | ✅ easy |
| C 英文难度 | ❌ easy | ❌ easy | ❌ easy 0.796 | ❌ easy | ✅ easy |

用最初的 `complexity{simple,moderate,complex}` 问法，**8/8 全部返回 `simple`**，包括「为千万级用户的系统设计一套限流、降级、熔断方案」。

`needs_web` 的 noul 在所有样本上都是 **0.75–0.95**，连「把变量名 x 改成 userName」都有 0.508 ⇒ 接近恒高偏置，不能直接当阈值用。

**三个可复用的结论**：

1. laya-multilingual 是**工单路由**分类器，不是通用难度评估器。它的训练分布不含「任务复杂度」这个概念。
2. 三种问法都有**首选项偏置**（A 偏 lookup、B 偏 easy、C 偏 easy）。
3. 它**自报的 `confidence` 是有信息量的**：`简单-改变量名` conf=0.038（分布近均匀）、`复杂-架构` conf=0.2697（近均匀）——这两种恰恰是它判错的情形；而 `简单-打招呼` conf=0.6402 是它判对的情形。**置信度低 = 它自己知道分不清。**

### 2.2 设计上的处置

因此 Jev 在本项目里**不是裁决者，是带弃权机制的辅助信号**：

- **启发式规则做主判定**（长度、代码块、关键词、结构），可靠且可单测。
- **Jev 只在同时满足两条时才被采纳**：`confidence >= min_confidence`（默认 0.35）**且** `p_top1 - p_top2 >= min_margin`（默认 0.25）。分布接近均匀就**弃权**，弃权时回落启发式。
- **上游不可用不是异常**：超时 / 404 / 未启动 / 连接拒绝，一律在超时预算内回落，**路由永不因此失败**。
- **`state` 必须截断**：edgeJev `max_len=1024`，发送前按可配置字符上限截断并保留尾部（真实问题往往在结尾）。
- **提供校准命令**：拿一批带标签样本跑完整分类链路，输出混淆矩阵与准确率。这是把「要不要更信任 Jev」变成**可验证结论**的唯一机制；在校准数据出来之前，默认权重就是「Jev 只在少数高置信样本上被采纳」。

> 这段失败轨迹保留在此，不是为了否定 edgeJev——它在**工单路由**这类它训练过的任务上又快又准（用户自己的 README 里有 billing 0.9873 / technical 0.999 的实测）。结论只是：**这个任务不在它的训练分布里**，要用它就得换一个问法或换一个模型，并用校准数据说话。

## 4. 本地模型

### 4.1 运行时探测

用户口径：**Ollama 全能力 + OpenAI 兼容端点**。

| 运行时 | 探测端点 | 能力来源 | 支持拉取/删除 |
| --- | --- | --- | --- |
| Ollama | `GET {base}/api/tags` | 原生 `capabilities[]`：`completion` / `vision` / `tools` / `thinking` / `embedding` / `audio` | 是（`/api/pull`、`/api/delete`） |
| OpenAI 兼容 | `GET {base}/v1/models` | `GET {base}/v1/models/{id}` 的根键推断，取不到时全部保守置 false | 否 |

默认端点（可增删）：

```
ollama      http://127.0.0.1:11434
lmstudio    http://127.0.0.1:1234
vllm        http://127.0.0.1:8000
llamacpp    http://127.0.0.1:8080
```

探测**并发**执行，单端点超时 1500ms，失败的端点返回 `reachable: false` + 原因而不是整体失败。全部不可达时 UI 明确显示「未检测到本地运行时」，并提示可手工填地址。

### 4.2 能力映射

Ollama `/api/tags` 实测返回（本机 0.35.1）：

```json
{ "name": "gemma4:12b-it-q4_K_M",
  "size": 8021618941,
  "details": { "family": "gemma4", "parameter_size": "11.9B",
               "quantization_level": "Q4_K_M", "context_length": 262144 },
  "capabilities": ["completion","vision","audio","tools","thinking"] }
```

映射规则（**保守优先**：宁可少标能力，不可多标）：

| ModelRef 字段 | 来源 |
| --- | --- |
| `upstream` | `name`（含 tag，`gemma4:12b-it-q4_K_M` 整体保留） |
| `alias` | `name`（可被用户改写） |
| `context_window` | `details.context_length`，缺失时 32768 并标「待确认」 |
| `supports_tools` | `capabilities` 含 `tools` |
| `supports_vision` | `capabilities` 含 `vision` |
| `supports_audio` | `capabilities` 含 `audio` |
| `supports_video` | **恒为 false**（本地运行时均无视频输入） |
| `supports_thinking` | `capabilities` 含 `thinking` ← **本轮新增字段** |
| `supports_stream` | `capabilities` 含 `completion` |
| `model_type` | 含 `embedding` → `Embedding`，否则 `Chat` |

`supports_thinking` 是本轮唯一的模型结构变更，加在 `ModelRef` 上并带 `#[serde(default)]`——旧库反序列化不受影响。

### 4.3 本地元数据

`models` 表新增一列 `local_json TEXT`，整包存：

```json
{ "runtime": "ollama", "family": "gemma4", "parameter_size": "11.9B",
  "quantization": "Q4_K_M", "disk_bytes": 8021618941, "capabilities": ["vision","tools"] }
```

理由与既有的 `price_json` / `overrides_json` 一致：拆定宽列会让 repo 与 domain 两处定义漂移。JSON 解析失败一律返回 `None` 静默降级，不 panic。

### 4.4 登记与拉取

- **一键登记**：把某个本地模型写成一个普通 Provider（dialect = `ollama` 或 `openai`）+ 一条 `models` 记录。登记后它与云端模型在候选链里**完全平权**，同样参与打分、降级与审计。
- **拉取**：`POST /api/pull` 是 NDJSON 流，逐行推 `status`。网关转成 Tauri 事件 `local-model://pull-progress` 推给 UI；UI 显示字节进度。取消即中断该 HTTP 流。
- **删除**：`DELETE /api/delete`，仅在 `models` 表里没有引用该 `upstream` 时允许，否则先提示会一并移除登记。

## 5. 智能模式

### 5.1 边界：新增策略，不改旧行为

`RoutingStrategy` 新增 `Smart`。**`auto` 的行为一字不改**——模式隔离要求：不开该模式的路径必须与改动前完全一致。

启用方式二选一，互不干扰：
- 全局策略设为 `smart`（设置页），或
- 客户端按请求用虚拟模型名 `smart`（临时覆盖，走 `Candidate.virtual_strategy` 这条现成通道）

### 5.2 分类链路

```
输入：ChatRequest
  │
  ├─ ① 硬规则（不可被模型覆盖，永远先跑）
  │     含 image/video                → Vision
  │     含 audio                     → Reasoning（音频转写需要长推理）
  │     tools && (上下文 > 8k 或轮次 > 6) → Reasoning
  │     显式点名模型（非 auto/smart）  → 跳过分类（用户已经决定了）
  │
  ├─ ② Jev 决策（edgeJev 默认 1200ms 预算）—— 只在下列两条同时成立时才采纳
  │     confidence >= min_confidence (默认 0.35)
  │     margin = p_top1 - p_top2 >= min_margin (默认 0.25)
  │     state 发送前按 max_state_chars (默认 2000) 截断，保留尾部
  │     ↓ 不成立 → 弃权
  │
  └─ ③ 启发式兜底（② 弃权 / 超时 / 404 / 服务未启动 / 置信不足）
        长度分档 + 代码块 + 关键词表 + 结构特征 → 永远返回非空结果
```

**弃权是正常路径，不是降级事故**。按 §2.1 的实测，本机 edgeJev 在多数样本上会弃权，
因此响应头 `X-Route-Classifier` 多数时候会是 `heuristic`。这是**如实反映模型能力边界**，
不是 bug；想提高 Jev 的采纳率，应该先跑校准（§5.7）再调阈值，而不是把 `min_confidence` 一路调到 0。

**兜底必须可失败**：测试里起一个必定超时的端点，断言分类结果仍非空且请求返回 200。

### 5.3 意图如何影响排序

`score.rs` 新增第 5 个乘法维度 `intent_fit`。**其余策略权重恒为 0（即乘 1.0）**，因此旧策略的排序结果逐位不变。

```rust
pub enum TaskClass { Simple, Vision, Reasoning }

pub fn intent_fit(class: TaskClass, c: &Candidate) -> f32 {
    let thinking = c.model.supports_thinking;
    let intel = c.provider.intelligence.clamp(0, 100) as f32 / 100.0;
    match class {
        // 简单任务：躲开思考模型，再按 intelligence 轻微降权
        TaskClass::Simple =>
            if thinking { 0.30 } else { (1.15 - 0.45 * intel).clamp(0.40, 1.0) },
        // 视觉：能力硬约束已在打分前过滤，这里不引入额外偏置
        TaskClass::Vision => 1.0,
        // 复杂任务：思考模型加分，没有思考能力的重罚
        TaskClass::Reasoning =>
            if thinking { (0.75 + 0.35 * intel).clamp(0.0, 1.0) } else { 0.45 },
    }
}
```

抽成纯函数是为了让每个分支都能被单测打穿。默认值表：

| 场景 | 值 |
| --- | --- |
| Simple × 思考模型 | 0.30 |
| Simple × 非思考、intelligence=20 | 1.00 |
| Simple × 非思考、intelligence=90 | 0.745 |
| Reasoning × 思考、intelligence=90 | 1.00 |
| Reasoning × 思考、intelligence=20 | 0.82 |
| Reasoning × 非思考 | 0.45 |

### 5.4 为什么不在流式中途插入工具结果

既有约束（`README.md`「上下文与降级边界」）：**首个流式字节输出后不得换上游**。若在流中做工具回合，就必须缓冲整段再重放，首包延迟从 ~300ms 涨到「两轮上游耗时之和」，且中途断流会丢掉已产生的字节。

因此联网搜索采用**预取式**：分类判定 `needs_web` 后，**在第一次上游调用之前**完成搜索并把结果注入上下文。客户端（Claude Code / Codex / Cursor）不需要知道网关背后做了什么，也不需要改任何工具定义。

非流式请求额外支持**工具回路**（客户端显式传 `web_search` 工具定义时，网关执行并回灌），但它是可选项，默认关闭。

### 5.5 提示词预优化（**已实现**）

Jev 不产文本，所以「预优化」拆成两步：

1. **Jev 判要不要改** —— 用 `clarity` 打分，**越低越含糊**。语义与 `needs_web` 相反：
   那个是「≥0.85 才联网」，这个是「<0.72 才改写」。
2. **判为需要时另调一次轻量模型做改写**，改写结果**替换发给上游的最后一条 user 消息**。

#### 为什么必须拆成两步

两步的失败模式完全不同，混在一起没法处理：

| 失败 | 后果 |
| --- | --- |
| Jev 挂 | 只是判定不出，回落启发式，**请求不受影响** |
| 改写模型挂或改坏 | **直接污染发给上游的提示词** |

所以 `needs_refine` 只在 Jev 被采纳时才有信号；启发式**恒返回 `false`** ——
关键词表判断不了「含糊」，猜错的代价是白白花一次模型调用并污染提示词。

#### 改写的护栏（`src/intellect/refine.rs`）

默认值全部偏向「不动」：

| 风险 | 挡法 |
| --- | --- |
| 超时 / 报错 | 用原文，**绝不阻断请求** |
| 提示词膨胀十倍 | 超 `max_chars` 判失败 |
| 模型加「好的，这是改写后的请求：」 | 剥掉 6 种常见包装前缀 |
| 长提示词被压成一句话 | 缩水超过 4 倍判失败 |
| 改写与原文相同 | 不算改写 |
| 反复改写 | **每请求最多 1 次，且不重试** |

**不重试是硬约束**：重试会让延迟翻倍，而且第二次改写的输入已经是改写结果，
改两遍的结果无法预测。

选目标时优先 `supports_thinking = false` 的模型 —— 改写是机械活，
派给会思考的模型是浪费 token。

#### 为什么是「替换」而不是「注入一条新消息」

两版指令并存会让模型困惑：要改写的那条和原文那条同时在上下文里，
模型可能回答错的那一条。所以**替换**最后一条 user 消息。原文不留在请求里，
但改写前后的字数写进审计（`requests.route_refine_note`），可人工核对改写幅度。

> **实现过程里改掉的一处**：初版第一修法是「只在 `HeaderValue::from_str` 失败时才
> 百分号编码响应头」，结果无效 —— `from_str` 会放行 0x80–0xFF 的原始字节，
> 中文写得进去但客户端 `to_str()` 读不出来。改为**无条件**编码。详见
> `docs/0.3.0验证记录.md` §4.3。

### 5.7 校准：把「该不该更信任 Jev」变成可验证结论（**已实现**）

IPC 命令 `calibrate_classifier(samples) -> CalibrationReport`，
另有 `calibrate_default_samples()` 直接跑本机实测的五条。

```rust
pub struct LabeledSample { pub text: String, pub expected: TaskClass, pub has_image: bool, pub has_tools: bool }
pub struct CalibrationReport {
    pub total: u32,
    pub matrix: BTreeMap<String, BTreeMap<String, u32>>,  // 行=真实，列=判定
    pub adopted_count: u32, pub adopted_correct: u32, pub adopted_wrong: u32,
    pub abstained_count: u32, pub abstained_but_heuristic_right: u32,
    pub heuristic_correct: u32,
    pub net_gain: i64,                                   // 唯一的决策依据
    pub wrong_confidences: Vec<f32>,                     // 降序
    pub worst_wrong: Option<SampleOutcome>,
    pub per_sample: Vec<SampleOutcome>,
    pub verdict: String,
}
```

#### 算的是什么

**混淆矩阵 + 净收益**：

```
net_gain = 采纳 Jev 后的正确条数 − 全部走启发式的正确条数
```

| net_gain | 含义 | 该做什么 |
| --- | --- | --- |
| > 0 | Jev 有价值 | 适度放宽阈值 |
| = 0 | 打平 | 不值得为它增加复杂度 |
| < 0 | 采纳它反而更差 | 加否决规则或直接关掉 |

报告还给出**错判的置信度分布**与**最危险的那一条**。这是关键：
错判置信度也很高（实测 0.747）就说明**阈值挡不住**——
模型可以又自信又错，调阈值解决不了，只能加规则或关掉。

#### 为什么参照系是启发式而不是人工标注

要回答的是「采纳 Jev 比不采纳好还是坏」，参照系必须是**不采纳时的结果**。
用人工标签只能评价模型，不能评价这条链路的策略。

代价要说清：这套报告**测不出「启发式自己错了而 Jev 对了」**。那需要另一份人工标注集——
而启发式本身就是规则写的，改它比换模型容易。

#### 校准不碰配置

只跑样本、只返回报告，**不擅自调阈值**。看完数据自己决定，命令擅自调就越权了。
每条样本都真打一次决策端点（`tests/calibrate.rs` 用计数器断言调用次数），
并**强制走 Jev 路径**——即使界面上把分类器设成 heuristic，
否则报告会退化成「启发式自己和自己比」。

#### 默认样本里刻意留了错判样本

「线上服务 500 白屏，帮我定位根因」是实测中 edgeJev 自信判错的那条。
留在集里报告才显示真实形态；删掉它会显示成一切正常，那种样本集没有诊断价值。

### 5.8 本地 edgeJev 的启停（**已实现**）

edgeJev **不随开机自启**（其 README 明确写了，重启后需手动重跑）。因此 Jev 配置带一组可选的启动参数：

```rust
pub struct JevConfig {
    pub base_url: String,          // 默认 http://127.0.0.1:8009
    pub model: String,             // 默认 rl-agent；edgeJev 忽略此字段，Ollama 侧需要
    pub timeout_ms: u64,           // 默认 1200
    pub max_state_chars: usize,    // 默认 2000，对齐 edgeJev 的 max_len=1024
    pub auto_start: AutoStartConfig,
}

pub struct AutoStartConfig {
    pub enabled: bool,             // 默认 false
    pub exe_path: String,          // ...\jev\.venv-runtime\Scripts\edgejev.exe
    pub model_dir: String,         // ...\jev\jev-int8
    pub port: u16,                 // 8009
    pub threads: u32,              // 8
    pub boot_wait_ms: u64,         // 默认 20000；加载 320MB ONNX 实测需 10–15 秒
}
```

`auto_start.enabled` 默认 **false**：启动外部进程是不可逆的副作用，必须由用户在界面上显式打开。
关掉这个开关时路径与改动前完全一致（`if cfg.smart_routing.jev.auto_start.enabled` 一道门）。

打开后，网关在分类前发现端点不可达时按需拉起。**但刻意不等它就绪**：

- 加载 320MB ONNX 实测需 10–15 秒，而这一步在**每条请求**的分类链路上；
- 等它会把首包延迟拉长十几秒，代价远超收益；
- 没就绪的后果是 Jev 请求失败 → **弃权 → 回落启发式**，完全可接受。

所以只做「探活 → 不在就 spawn → 立刻返回」。就绪与否由后续 Jev 请求自己探。

#### 三个必须处理的问题

1. **子进程不能继承 stdio**。Tauri 在 Windows 上没有控制台，子进程输出会把管道写满，
   然后它阻塞在写日志上——表现是「服务起来了但不响应」。一律 `Stdio::null()`。
2. **不能重复拉起**。用 `Mutex<Option<Child>>` + `try_wait()` 存活检查守住，
   否则端口冲突会让两个都起不来且报错难懂。
3. **只停自己拉起的**。没有句柄就返回 `false`，绝不杀用户手动启动的那个 edgeJev。

#### 命令行参数

对着本机实测的 `edgejev serve --help` 拼：

```
serve --model <model_dir> --host 127.0.0.1 --port <port> --threads <n> --provider cpu
```

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| `--host` | 写死 `127.0.0.1` | 决策端点没有任何鉴权，绝不能绑 `0.0.0.0` |
| `--provider` | 写死 `cpu` | 默认 `auto` 会去探测 CoreML；延迟敏感路径上不留这种不确定性 |
| `--api-key` | **不传** | 本仓库没有决策端点鉴权配置，传空值反而让某些版本解析失败 |
| 探活路径 | 只打 `/health` | `/v1/systemone` 会真跑一次推理，而这步每条请求都要走 |

**网关一个字都不猜路径**：只使用用户显式填的值，猜错就是启动了用户没要求的东西。

### 5.10 启动降级：配置坏了也必须起来（**已实现**）

这不是智能模式的功能，是它带来的**后果**：新增了 `SearchBackendKind` / `SmartClassifier`
等枚举后，一个拼错的枚举值会让 TOML 解析失败，而原来的启动路径是
`boot.mark_error()` 后 `return` —— 网关不监听，窗口只剩空壳。

实测症状：配置里写 `backend = "duckduckgo"`（真值是 `duck_duck_go`），
**整个应用打不开**，且界面上没有任何提示能指回是哪个键写错了。

改为**降级而不是失败**：

```
配置解析失败
  ├─ 原文件挪走 → config.corrupt-<unix秒>.toml（不删，可回滚）
  ├─ 写回默认配置
  ├─ 照常启动（网关监听、窗口正常、可用默认设置）
  └─ BootStateView.warning 带出「哪个键错了 + 备份在哪」
```

两条设计约束：

1. **`status` 仍然是 `ready`，不是 `error`。** 降级 ≠ 启动失败。混淆这两者会让
   「加载失败」提示和横幅同时出现，用户不知道该看哪个。
2. **必须显式告知**。静默降级比报错更糟：界面上一切正常，用户以为自己的
   供应商、模型、路由设置都生效了，实则全部回退到默认值。

前端 `main.tsx` 的 `waitForBackend()` 从「等 status 变成 ready」改为
「ready 就返回 `state.warning`」，由 `App.tsx` 渲染成可关闭的横幅。
断言见 §9。

配套测试：`坏配置_应回退默认且把原文件挪走` +
对照组 `好配置_不得被降级_对照组`。
**对照组是必须的**：只有前者的话，一个「永远降级」的实现也能让测试通过，
而界面上会常驻一条永远显示的噪音。

### 6.1 后端（用户口径：多后端可配置 + 免 Key 兜底）

**先说一件必须先说清的事：同一个后端有两套字符串，这不是笔误。**

| 用途 | 由谁产出 | `SearXng` 的值 | `DuckDuckGo` 的值 |
| --- | --- | --- | --- |
| **配置文件 / 前端下拉** | serde `rename_all="snake_case"` 自动生成 | `sear_xng` | `duck_duck_go` |
| **响应头 / 审计展示** | 手写 `search::backend_code()` | `searxng` | `duckduckgo` |

两套值**用途不同、不可互换**：

- 写进 `config.toml` 或作为 `<option value>` 的必须是**第一套**。
  写成第二套 → TOML 解析失败 → **整个应用打不开**（不是「选不中」）。真踩过。
- 出现在 `X-Route-Search` 里的是**第二套**，因为它给人和日志看，`searxng` 比
  `sear_xng` 好读。

`BingCn` 两套恰好同形（都是 `bing_cn`），所以它看不出差别 —— 那是巧合，
**不是可以省掉检查的理由**。新增后端时两处都要改，且都要有测试。

**验收判据**：`tests/config.rs` 的 `四个搜索后端的枚举名必须与前端下拉一致`
逐字比对 `SearchBackendKind` 的 serde 值与 `src/api.ts` 的 `SearchBackendKind`。

下表列的是**配置值**（第一套）：

| 后端 | 端点 | 凭据 | 备注 |
| --- | --- | --- | --- |
| `tavily` | `POST https://api.tavily.com/search` | API Key | 为 LLM 设计的检索，直接给 `content` 摘要 |
| `brave` | `GET https://api.search.brave.com/res/v1/web/search` | Subscription Token | 独立索引 |
| `sear_xng` | `GET {base}/search?format=json` | 无（自建） | 隐私优先，可指向公网实例 |
| `duck_duck_go` | `POST https://lite.duckduckgo.com/lite/` | **无** | 兜底，可用性无保证 |
| `bing_cn` | `GET https://cn.bing.com/search` | **无** | 免 Key 且本机可达，实测 248 ms，见 §6.6 |

回落到上游原生搜索（OpenAI `web_search` / Gemini `google_search` / Anthropic `web_search`）**不做注入**，只做透传：`normalize_responses_tools` 现在把未知工具类型直接丢弃（`server.rs:1405-1408`），改为一律透传给支持的上游是独立的一轮工作，会引入「上游 400」的兼容风险，不与本轮捆绑。
### 6.2 凭据存储

搜索 API Key **不进 `config.toml`**（那是明文落盘、会随项目快照传播）。新增表：

```sql
CREATE TABLE IF NOT EXISTS app_secrets (
  name TEXT PRIMARY KEY,
  value_enc TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

值走既有 `crypto.rs` 的 AES-256-GCM。读取路径 `repo::get_secret(pool, "search.api_key")`，UI 永远只回传掩码（与 `ProviderView::api_key_masked` 同款处理）。

### 6.3 注入格式

```
[联网搜索结果] 查询：<query>  来源：<backend>  命中：<n>
1. <title> — <url>
   <snippet>
2. ...
```

作为一条 `system` 消息插在**最后一条 user 消息之前**，保证模型先看到原始请求再看到检索材料。不注入到 system prompt 开头——避免长检索结果挤掉真正的指令。

### 6.4 失败语义

- 后端返回 401/403 → 标记该后端凭据失效，**本请求回落下一后端**，不回落到免 Key（避免用错误的凭据反复打）。
- 全部后端不可用 → 响应头 `X-Route-Search: failed`，请求**继续正常发往上游**（模型自带的知识仍可能答对），并在审计里记失败原因。不阻断请求。
- 超时 8s。

### 6.5 免 Key 兜底的手写解析

`Cargo.toml` 没有 HTML 解析依赖，按铁律不加。所以 DuckDuckGo 走 `lite.duckduckgo.com`——它的 HTML 极其规整，只需两个正则式的手写扫描：

- 链接：`<a … class="result-link" href="URL">TITLE</a>`
- 摘要：紧随其后的 `<td class="result-snippet">…</td>`

实体解码只需覆盖 `&amp; &lt; &gt; &quot; &#39; &#x27; &nbsp;`。解析失败返回空列表而不是抛错——空列表和「没搜到」在注入文本里无法区分，所以额外用 `X-Route-Search-Hits: 0` 标记，让调用方能判别。

**URL 与展示文本用两套解码，不能混用**（这是本轮静态审查裁定的一条）：

| 用途 | 函数 | 行为 | 理由 |
| --- | --- | --- | --- |
| 展示文本（标题、摘要） | `decode()` | 实体 + 百分号 | 给人看，要还原 |
| 链接（`href`） | `decode_entities()` | **只解实体** | href 本来就是已经百分号编码好的地址。解开 `%20` 得到带裸空格的不可用链接，解开 `%26` 会把查询参数的分隔符也改掉——解出来的地址语义已经不是原来那个了 |

百分号解码按字节累积、末尾一次性 UTF-8 解码。**不能**逐个 `%XX` 立刻转成 char：
中文 URL 常是 `%E4%B8%AD` 这样的三字节序列，逐字节解码会得到三个乱码字符。

另有两处防御性处理，都是为了「宁可少一条结果，也不要静默给出错的」：

- `uddg=` 跳转链接解包：DuckDuckGo 有时把结果包成 `/l/?uddg=<百分号编码的目标>`，
  不解包的话注入上下文里全是点不开的跳转地址；解不出绝对 `http(s)://` 就整条丢弃。
- 锚点按**类名**匹配（`result-link`）而不是 `class='result-link'`：上游改一次引号风格
  就会让整页解析静默返回空列表，而界面只显示「没搜到」，永远不会有人发现解析器已坏。

> **本机实测前提（2026-10-04 首测 / 2026-10-05 补测）**：
> `lite.duckduckgo.com` / `html.duckduckgo.com` / `duckduckgo.com` 在这台机器上
> **全部超时**，`api.search.brave.com` 同样超时，`api.tavily.com` 可达但需 Key。
> 当时据此写下「免 Key 兜底在这台机器上不成立」——
> **这个结论的范围太窄，已被 2026-10-05 的补测证伪**：它只覆盖了海外引擎。
> 国内引擎本机全部可达，详见 §6.6。逐条实测数据见
> [`0.3.0验证记录.md`](0.3.0验证记录.md) §2.4 与 §4.12。

### 6.6.1 抓必应时踩到的三个 bug（都不是「解析器写错了」这种笼统问题）

**① UTF-8 边界切错 —— 会毁掉全部结果**

`h2.find("<a")` 返回的是**相对偏移**，写成 `let a_end = h2[a_at..].find('>')`
再当绝对下标用。中文页面必然触发：`&s[a..=b]` 在多字节字符中间切开。

```
地址 https://a.example/  →  https://a.exampl
标题 第一个中文标题       →  e/"第一个标题
```

`h2_end` 同样的错也一起修了。回归测试：`必应_中文标题与地址不得被字节偏移截断`。

> 这条是本项目**最贵的一个坑**：它同时适用于任何手写 HTML 扫描。
> `find()` / `find_map()` 返回的永远是**相对于被搜索串**的下标，
> 要用必须加回基准，而基准往往不在同一层循环里。

**② `&#0183;` 解不掉**

必应摘要在日期后固定放 `&ensp;&#0183;` 当分隔符。两处叠加：

- `ENTITIES` 表里没有 `&ensp;`（后来补了 `&ensp; &emsp; &thinsp; &hellip; &middot; &times; &laquo; &raquo; &rarr;`）；
- `decode()` 与 `decode_entities()` **各写一份实体分支**，改一处漏一处。

补了实体仍不解，追下去发现位数上限算错了对象：

```rust
if digits.is_empty() || digits.len() > 8   // ❌ digits 是整段剩余串，不是数字部分
```

`&#0183;&ensp;` 的剩余串 12 字节 → 整条被丢弃。改成按**分号位置**判：

```rust
if semi_at == 0 || semi_at > 8 || digits.len() < semi_at   // ✅
```

十六进制形式还少算了 `x` 那一字节（症状：`A·;B`）——
`&#xB7;` 解出 `·` 却把分号留在原地，所以消耗字节数要 `2 + prefix_len + semi_at + 1`。

**③ 两个解码函数必须有一致性测试**

`decode()` 与 `decode_entities()` 是**两份独立实现**，这是设计上就该合并但会破坏
「URL 不解百分号」约束的取舍。代价是必须用测试钉住一致性：

```rust
#[test]
fn 实体_两个解码函数必须给出一致结果() { /* 同一输入，两函数必须同输出 */ }
```

只看「`decode_entities("&#0183;")` 对不对」是**测不出来的**——
单独输入时它是对的，坏的是**串联**场景（`A&ensp;&#0183;&ensp;B`）。

```rust
// config.rs，全部 #[serde(default)]，旧 config.toml 自动兼容
pub struct AppConfig {
```

## 10. 风险与已知边界

| 风险 | 处置 |
| --- | --- |
| Jev 模型未安装 | UI 明确显示未安装并给 `ollama pull <model>` 命令；分类回落启发式，不报错 |
| 决策模型抢显存 | Jev 默认不自动拉取；启用前 UI 显示模型名与用户自选 |
| 免 Key 搜索随时失效 | 只作最后兜底；界面标注「可用性无保证」；失败不阻断请求 |
| 预取增加首包延迟 | `needs_web` 为假时零额外调用；为真时多一次搜索往返，头部显式回传 `X-Route-Search` |
| 意图误判导致选错模型 | 分类结果与依据全部回传响应头并落审计；可关；`auto` 路径完全不受影响 |
| 手写 HTML 解析随上游改版失效 | 解析失败返回空列表 + `X-Route-Search-Hits: 0`，不抛错；解析器单独单测 |
| **枚举值拼错 → 整个应用打不开** | 启动降级（§5.10）：备份原文件 + 回退默认 + 横幅告知；前后端枚举名由测试钉死 |
| **必应格式变化（它是 SERP 抓取，非官方 API）** | 空结果返回 `SearchError::Malformed` 而非静默空列表；`X-Route-Search-Hits: 0` 可判别 |
| **结论范围越界** | 「海外引擎不可达」不等于「免 Key 兜底不成立」——见 §6.6。写结论时必须列出测过的范围 |
| **本地 27B 在 CPU 上极慢** | 实测 1.1 秒/token、一条长回答 271 秒；`upstream_timeout_secs` 默认 120→**600**，否则本地模型场景必然 504 |

### 6.7 为什么不做百度 / 搜狗 / 360：实测结论，不是猜测

§6.6 的可达性表只测了「有没有回 HTTP 响应」。补测了**响应里有没有结果**，
两家当场出局：

| 引擎 | HTTP | 实际内容 | 结论 |
| --- | --- | --- | --- |
| 百度 | **302** | 跳 `wappass.baidu.com/static/captcha/tuxing_v2.html`（图形验证码） | **IP 级封禁**，解析器无从下手 |
| 搜狗 | **302** | 跳 `sogou.com/antispider/?antip=web_hd`（反爬页） | 同上 |
| 360 | 200，790 KB | 13 个 `<h3>`，但链接全是 `e.so.com/search/eclk?p=…` 加密跳转 | 能解析出标题，**拿不到可用 URL** |

**「HTTP 200 / 可达」和「能拿来做搜索后端」是两件事。**
上一版文档只测了前者就写进可用性表，是一次**用错判据**的结论 ——
与 §6.6 那次「把没测过的写成不行」是同一条教训的两面：
一次是范围越界说成不行，一次是判据不足说成可用。

360 那条尤其值得记：它的 `eclk?p=` 是**加密参数**，解出来是 JS 重定向而不是
明文目标 URL。就算写了解析器，注入进模型上下文的也是一堆点不开的地址 ——
功能只完成一半，而用户看到的是「搜到了但链接没用」，比明确报错更难排查。

结论：`bing_cn` 已覆盖「免 Key + 中文结果 + 可用 URL」这三个条件，
再加三个解析器换不来可用性，只增加维护面（每家改版都要跟）。
真要接这三家，正确路径是走它们的**官方开放平台**（要 Key / 要资质），
而不是继续抓 SERP。
