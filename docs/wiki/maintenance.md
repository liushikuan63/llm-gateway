# 维护与扩展

## 每个里程碑的交付条件

1. 先确认当前生产入口与真实缺口；历史“待实现”不等于现在缺失。新增逻辑有有效失败证据、正反控制及适用回归。
2. 关键模块注释说明设计原因、不变量、await/取消、失败不重试和兼容边界，并链接相关 Wiki。不要逐行解释代码，也不要把凭据写入注释。
3. 功能、注释和 Wiki 同一候选更新，源码互链可达，命令实际存在，配置只有占位值；未验、未安装及已知限制明确列出。
4. 独立只读 QA 核对链接、命令、事实和证据范围，执行现有 `npm run verify:plan` 文档门禁。文档通过不能替代行为验证。
5. 在最终输入上统一适用完整门禁，绑定 Windows 资产、源清单、包及安装结果；真实外部步骤独立记录。已完成且相关输入未变的检查不因补写状态重复执行。
6. 实体包由独立于实现者的验收执行者在兼容真实环境实际安装、启动并验证关键流程。唯一主线冻结对象并串行交接安装执行权；独立代理可以在用户同一台 Windows 上执行，但必须明确机器归属，不能称为另一台或云电脑。保留验收者、环境、包 SHA256、HEAD+dirty 清单、命令/退出码、日志截图和失败原件。构建、自测或只读复审不能替代该流程。

## 所有权与并行

唯一主线集成共享源码、DTO、配置、数据库、构建、发布资源和安装。最多两个隔离辅助先只读确认差距，再由主线明确释放准确范围；隔离快照包含相关当前脏源码，不能只基于旧 HEAD。回传补丁、输入哈希、真实失败/通过、未验边界与计时，主线复核变化后应用。

Search 辅助限定搜索内核与对应测试；设置、出站、公开配置及 API 归主线。refusal 辅助在主线使用同一文件时保持只读设计，不与主线同时写 `desktop_chat.rs`。不启动第二套重型流水线。

## 记录与扩展原则

每阶段记录带时区的开始/结束及分析、实现、测试、构建安装、复审返工、外部等待。重叠时间不重复算到同一人的分类中；并行工作量与用户等待墙钟分别统计。未记录的历史段不补造。前三个可比小批次后再校准同类 ETA，不从 token、测试数或截图数推算完成百分比。

新增后端先定义失败、取消、总期限和来源语义，再做配置/界面接线。新增 DTO 先确认旧文件及旧调用方兼容。改 schema、路由权重、计费政策或网络安全设置先按项目规则形成方案；普通扩展授权不包含发布、合并、提交推送、付费或变更凭据。

MSI 行政提取不算 MSI 实装，云 Linux 构建不能证明 Windows/macOS 实装。缺少兼容平台时明确未实装验证及所需环境；已有 Mac 包按已有证据复用，不为本轮 Windows 候选重做。
