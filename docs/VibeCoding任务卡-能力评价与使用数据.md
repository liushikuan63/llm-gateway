## 设计边界

价格、声明能力与实测表现分别给出依据。模型价格属于配置/公开目录数据，并非必须等待请求样本才能获得；延迟、吞吐与任务匹配属于实测/反馈数据，不能用缺失值、默认中档或主观能力分冒充。原有分数仍按现有算法展示，实施新指标时必须解释数据覆盖率、来源、采样窗口及回退方式。

能力声明分支持、明确不支持、未知，保留官方文档/模型元数据/手工覆盖/协议实测的来源及时间。模型宣称支持与当前供应商、协议、账号实际可用分别记录。先按请求必需能力过滤，再评价候选，不能用高智能分抵消多模态、工具或上下文条件不满足。

## 数据口径与实现约束

- 经桌面/CLI 包装返回的结束时间不能自动称真实 TTFT；无法观测第一有效 token 的路径标记为不可测或代理估计。重试、级联每一跳分别采样，成功请求的总耗时不能全部归属最后一跳。
- 缓存直接返回与正常供应商生成分别计样本；失败与超时保留，不把异常剔除后呈现虚假的低延迟。价格时段、上下文分档必须使用单次请求条件，不能把跨天合计 token 当作一次长上下文请求。
- 任务匹配与质量需要人工/用户反馈或有判据的基准，不能由模型自称正确。延迟、效率与质量之间的权衡应可解释，并保留样本稀疏时的稳定策略。
- 优先沿已有 RequestLog/trace、模型能力与 capability_sources、定价和解释结构补充。当前 schema 不足时先形成迁移方案并遵循项目约定；不在本轮直接加表或改分数。
