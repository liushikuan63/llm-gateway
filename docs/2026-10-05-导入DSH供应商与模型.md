# 2026-10-05 批次：把 DSH 的供应商与模型导入本机网关

## 一、需求与范围

把 DSH（本机 `~/.dsh-beta/profiles/desktop/cordis.patch.yml` 里 `llm-pi-ai` 的
provider 字典）里的**全部供应商与模型**一次性加入本机网关，并让它们真正可调用。

导入结果：8 个供应商 / 131 个模型（网关侧去重后 `/v1/models` 暴露 119 个模型名）。

| 供应商 | 协议 | 模型数 | API 地址 |
|---|---|---|---|
| commandcode | openai | 72 | `https://api.commandcode.ai/provider/v1` |
| zai-coding-cn | openai | 10 | `https://open.bigmodel.cn/api/coding/paas/v4` |
| agentrouter | openai | 6 | `https://ps.air-outer.com/v1` |

**故意没导入的**：`llmgw`。它在 DSH 里指向 `http://127.0.0.1:15721/v1`，
就是本网关自己；把它再登记成上游会形成自环。

所以每个都写入了密钥；该文件全程不进上下文、不落进仓库。

## 二、为什么不走界面

Provider 的增删改只有 Tauri IPC 命令（`commands.rs::upsert_provider`），
对外 HTTP 只有 `/v1/*` 与 `/gw/*`，**没有写入接口**；而
`upsert_provider` 内部在落库后还会调 `state.gateway.reload_providers()`
刷新内存路由表。绕过界面直写 SQLite 会命中「界面显示已保存、运行时毫无变化」
的经典症状（约束 7：配置改动要写两把锁）。

因此新增 `src-tauri/examples/import_dsh_providers.rs`，**复用生产代码**：

- `crypto::encrypt` —— 密文格式的唯一来源，另写一套必然解不开；
- `model_catalog::normalize_base_url` —— 与界面「获取支持模型」同一套地址规范化；
- `repo::upsert_provider` —— 与界面保存同一套写入顺序（先 provider、再整体替换 models）。

写入完成后重启应用（`AppState` 只在启动时从 DB 装载 provider），
新供应商才进入运行时路由表。实测：重启前 `/v1/models` 只有 3 个模型，
重启后 119 个。

## 三、映射决策

| 字段 | 取值 | 理由 |
|---|---|---|
| `dialect` | DSH 的 `api` 映射（本次全是 `openai-completions` → `openai`） | 上游都是 OpenAI 兼容 |
| `base_url` | 原样保留 DSH 的版本前缀 | 网关只在 base_url 后**追加** `/chat/completions`；再补 `/v1` 会拼出 `/v1/v1/...`（`intellect/refine.rs` 注释记了这个坑） |
| `zai-coding-cn` 的地址 | `https://open.bigmodel.cn/api/coding/paas/v4` | DSH 配置里没写，取 pi-ai 内置默认值（`providers/zai-coding-cn.js`） |
| `openrouter` 的地址 | `https://openrouter.ai/api/v1` | 同上 |
| `context_window` | DSH 的 `contextWindow`；pi-ai 目录里有则优先用它 | 参与网关的容量检查与压缩判断，填大可能被上游拒绝 |
| `supports_thinking` | 有 `reasoningEfforts` / `reasoning` 才为真 | 误标会把 reasoning 参数发给会 400 的模型 |
| `supports_vision` | 仅当 `inputModalities`/`input` 含 `image` | 同上，能力保守 |
| `model_type` | 模型 id 含 `image` 判为 `image`，其余 `chat` | 图片生成模型走 `/v1/images/generations` |
| `price` | pi-ai 目录里有的（openrouter、zai）按每百万 token 写入，`source=catalog` | 没有它界面永远显示「未知」费用 |
| `priority` | 全部 100 | 首选项交给用户在界面上定，导入不替用户决策 |
| `enabled` | 全部启用 | 8 个都有密钥 |

14 个模型名同时存在于两个供应商（如 `deepseek-v4-flash` 在 agentrouter 与
sensenova、`gpt-image-2` 在 geeknow 与 shitapi）。这是网关既有语义：
同名会产生多条候选，再按策略排序；也可以用 `provider:model` 精确限定。

## 四、验证（每条都带可失败判据）

1. **导入器自带回读**：写完立刻 `list_models_of` 比对数量，并用
   `crypto::decrypt` 验刚写入的密文——任一不符就 `bail`。
2. **断言能失败**：把清单里的 `context_window` 改成 0、给 openrouter 塞
   `prompt = -1`，两次都以退出码 1 失败，并打印具体原因。
3. **真库落库回读**：9 个供应商 / 134 个模型（8 新 + 131 新模型 + 原有 3 个本地模型），
   8 个供应商 `api_key_enc` 均非空。
4. **重启前后对照**：重启前 `/v1/models` = 3 个，重启后 = 119 个；
   逐个抽查 `claude-sonnet-5 / glm-5.3-flash / deepseek-v4-flash / gpt-image-2 /
   spark-x2.5-4b / stealth/space-bunny-alpha / sensenova-6.7-flash-lite /
   poolside/laguna-s-2.1-free` 全部 present，对照组 `no-such-model-xyz` absent。
5. **真实链路**：`POST /v1/chat/completions` model=`openrouter/free` → HTTP 200，
   审计表记录 `routed_provider=openrouter / status=200 / prompt=28 / completion=16`；
   同一入口请求不存在的模型 → 404。

## 五、逐家直连初测

导入只是「配好了」，不等于「上游肯理你」。逐家直连实测（Python `urllib`）：

| 供应商 | 直连结果 | 结论 |
|---|---|---|
| openrouter | HTTP 200 | ✅ 可用，已通过网关端到端验证 |
| commandcode | HTTP 403 `error code: 1010` | ⚠️ Cloudflare 按客户端指纹拦截 |
| zai-coding-cn | HTTP 429「GLM Coding Plan 当前训练中……您之前的订阅已完成，请尽快续订」 | ⚠️ 订阅到期，账号侧问题，补 Key 无解 |
| agentrouter | HTTP 401 `unauthorized client detected` | ⚠️ 上游拒绝该 Key |
| shitapi | HTTP 403 `INSUFFICIENT_BALANCE` | ⚠️ 余额不足 |
| sensenova | HTTP 404 `model is not found` | ⚠️ DSH 配置里的 `sensenova-6.7-flash-lite` 不是该上游的真实 id |
| maas-api / geeknow | 未发付费请求 | 未验证 |

### ⚠️ 本节曾写错一处，已在第二轮更正

上面「commandcode 被 Cloudflare 拦、网关出站指纹不同」是**错的**。第二轮拿到的证据：

- 网关侧那条 `poolside/laguna-s-2.1-free` 的 429，响应体是上游 JSON
  `{"error":{"message":"Upstream model provider is temporarily unavailable","type":"rate_limit_error"}}`，
  不是 Cloudflare 的 HTML —— 说明 **reqwest 根本没被 CF 拦**；
- `gpt-5.4-mini` 换成 `stealth/space-bunny-alpha` 后，网关侧直接 200。

被 403 的是 **Python 的 TLS/HTTP 指纹**（CF 1010 只针对脚本客户端），被 429 的是
那个具体模型当时不可用。教训：直连探针的结果不能直接外推到网关，
必须两边各测一次，否则会把「客户端差异」误判成「供应商不可用」。

## 六、重跑与回滚

```powershell

& .\scripts\cargo-env.ps1
cargo run --release --example import_dsh_providers -- <providers.json> <keys.json> [--dry-run] [--db <path>]
```

- `--dry-run`：只校验与计数，不写库；

回滚：导入前的整库快照在
`%TEMP%\llmgw-import\gateway-before-dsh-import-20261005-150924.db`。
恢复方式：退出应用 → 用该文件覆盖 `%LOCALAPPDATA%\llm-gateway\gateway.db`
（同目录的 `-wal` / `-shm` 一并删除）→ 重新启动。

## 七、清单是怎么生成的

生成器已落进仓库：`scripts/gen-dsh-manifest.mjs`。关键点：

- provider 字典取 `cordis.patch.yml` 中所有 `config.providers` 的并集；
- `baseURL` 缺失的用 pi-ai 内置默认值补（`zai-coding-cn`、`openrouter`）；
- `contextWindow` / `input` / `cost` 优先用 `pi-ai/dist/providers/data/<id>.json`
  的目录数据补齐；
- 密钥从 `.credentials.yaml` 的 `refs:` 取出，写进**单独的** `keys.json`，
  该文件用完即删，不进仓库、不进日志；
- `providers.raw.json` 是**不做任何修正**的原始清单，专门给探测器当输入。

完整管道（第二轮起）：

```powershell
$d = "$env:TEMP\llmgw-import"
node scripts/gen-dsh-manifest.mjs --out $d                       # 原始清单
node scripts/probe-upstream-models.mjs --config "$d\providers.raw.json" --keys "$d\keys.json" --out "$d\probe-result.json"
node scripts/gen-dsh-manifest.mjs --out $d --probe "$d\probe-result.json"   # 修正后的清单
& .\scripts\cargo-env.ps1
cargo run --release --example import_dsh_providers -- "$d\providers.json" "$d\keys.json"
```

## 九、据此做的四个修正

1. **协议拆分**：commandcode 是混合协议中转——`claude-*` 会返回
   `400 must be called via /provider/v1/messages (Anthropic Messages shape)`。
   放错方言的后果不是「用不了」，而是报错指向协议、让人以为是网关坏了。
   已拆出 `commandcode-anthropic`（`anthropic` 方言、同 base_url、8 个模型），
   网关在 base_url 后追加 `/messages`，正好命中该中转要求的路径。
2. **剔除死模型**：SenseNova 的 4 个 id（`sensenova-6.7-flash-lite`、`u1-fast`、
   `u1.5-lite`、`u1.5-fast`）上游目录已无，一律 404，删掉；同时按上游目录补上
   DSH 漏掉的 `deepseek-flash`、`deepseek-v4.1-flash`。
3. **模型级参数覆盖**：`sensenova/kimi-k3` 报
   `400 field Temperature invalid, only 1 is allowed for this model`，
   写入 `overrides.temperature = 1`，导入器落库前按 `ModelOverrides::validate()` 校验。
4. **管道顺序修正**：探测器必须以**原始清单**为输入。最初拿「已修正清单」当输入，
   结果上一轮被剔除的 4 个模型因为没有判定值而在下一轮原样回来——修正变成一次性动作。

# 第三轮：凭据已死的供应商拖死了「自动分流」

## 十二、症状与根因

DSH 一轮报 `AUTH / API 密钥无效`，模型选择器显示「网关自动分流」。
网关审计里对应的是 `requests.id=72`：`model=auto`、`status=401`、`error=auth_failed`、
**`fallback_attempts=0`、`routed_provider=NULL`**，候选链只有一个：

```text
- agentrouter/claude-opus-4-8 status=401 retryable=False 7828ms
    {"error":{"message":"unauthorized client detected, ..."}}
```

完整因果链：

1. 本地 ollama 供应商（priority=10，本该第一个命中）当时不可用；
2. 候选链落到 priority=100 的一批，第一家是 `agentrouter`；
3. agentrouter 上游对 401 返回 `retryable=false`（`failover.rs::is_fatal_auth`
   把 401/403 定义为「需要用户换 Key」）；
4. 网关因此**当场终止整条候选链**，`fallback_attempts=0`；
5. 健康的 commandcode / openrouter / sensenova / maas-api 一个都没被试；
6. 网关把 401 回给 DSH，DSH 显示成「API 密钥无效」——**指向客户端，真正原因在上游**。

两个容易走错的方向，都实测排除了：

- **不是密钥不一致**：DSH 的 `LLMGW_API_KEY` 与网关 `unified_key` 的 SHA256 完全相同；
  审计里 `client=local-unified-key` 说明入站鉴权是通过的。
- **不是模型失效**：`agentrouter` 的模型在上游目录里都活着，只是这把 Key 被拒。
  所以另一批「失效模型扫描与批量删除」治不了这个问题——那是模型级（404），
  这是**供应商级凭据/额度**问题。

## 十三、做法

不靠猜，靠第二轮建好的探测结论：一家供应商的**所有模型**都被上游按凭据/额度拒绝时，
在清单里写 `enabled=false`，并把原因写进 `note`。判据只用响应正文：

```js
verdict === 'auth_failed'
  || /1309|INSUFFICIENT_BALANCE|subscription|Subscription|unauthorized client/i.test(note)
```

命中：**agentrouter**（401 unauthorized client）、**shitapi**（INSUFFICIENT_BALANCE）、
**zai-coding-cn**（1309 GLM Coding Plan 订阅到期）。
sensenova 有一个模型 `auth_failed` 但另有 4 个 `ok`，因此**不停用**——
这条对照保证了规则不是「见 401 就停」。

实现落两处：`gen-dsh-manifest.mjs` 产出 `enabled` 字段，
`import_dsh_providers.rs` 从清单读取（此前硬编码 `enabled: true`）。

## 十四、修后实测

| 请求 | 结果 | 含义 |
|---|---|---|
| `gpt-6-astra`（只存在于 agentrouter / shitapi） | **404，33ms** | 已停用的供应商不在候选链里，连上游请求都没发出 |
| `glm-5.3`（只存在于 zai） | **404，1ms** | 同上 |
| `glm-5.2`（sensenova，启用） | 200，883ms | 启用中的供应商不受影响 |
| `auto`（DSH 的路径） | 200，19.6s，落到本地 ollama | 自动分流恢复正常 |

## 十五、仍未修的脆弱点

**只要「启用中」的供应商密钥失效，`auto` 仍然会整条终止**。这次只是把三个已知的坏供应商
移出了候选链，并没有改变失效发生时的行为。彻底修需要改 `failover.rs` 的语义
（鉴权失败后跳过该候选、只在没有带 Key 的候选时才返回 401），
这属于路由语义变更，且该文件刚被另一批工作改动过，故留待裁决。
