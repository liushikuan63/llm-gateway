## 一、DSH 凭据：`apiKeyEnv` 指的是文件键名，不是环境变量

### 现象

在 `~/.dsh-beta/profiles/desktop/cordis.patch.yml` 里配置好 provider 后，
DSH 报：

```
MISSING_CREDENTIAL: llm-pi-ai: no credential for provider route "llmgw";
its profile resolves LLMGW_API_KEY, which is not set
```

### 根因

我此前给的修复建议是"设置环境变量 `LLMGW_API_KEY`"——**这个建议本身是错的**。

DSH 的 API Key 存在 `~/.dsh-beta/.credentials.yaml` 的 `refs:` 下，
`cordis.patch.yml` 里的 `apiKeyEnv` 是**那个文件的键名**，不是环境变量名：

```yaml
# ~/.dsh-beta/.credentials.yaml
refs:
  LLMGW_API_KEY: <REDACTED_GATEWAY_API_KEY>
```

### 两个踩坑点

1. **缩进必须是 2 空格**（与 `records:` 下的键同级）。写成 4 空格时
   整个 YAML 解析失败：`YAMLParseError: Nested mappings are not allowed`。
2. **改完要重启宿主**。凭据与插件行都不热加载。

### 顺带发现

交叉检查全部 provider 后发现另有 5 个也缺凭据
（`zai-coding-cn` / `sensenova` / `maas-api` / `geeknow` / `shitapi`）。
已用改动前的备份确认这是**既有状态**，与本批次无关。

## 二、开机自启（新增能力）

### 方案选择

托盘常驻**早就存在**（关主窗口只是隐藏，`should_hide_to_tray`），
所以缺的只是自启本身。三种实现的取舍：

| 方案 | 结论 |
|---|---|
| 用户级注册表 `HKCU\...\Run` | ✅ 采用。免提权、用户可在"任务管理器→启动"里关掉、零新增依赖 |
| `tauri-plugin-autostart` | ❌ 违反项目硬约束"不许加依赖" |
| Windows 服务 | ❌ 需管理员权限 + msi 特殊配置，且当前架构是带 GUI 的托盘应用 |

### 为什么写 `HKCU` 而不是 `HKLM`

`HKLM` 需要管理员权限，普通用户直接失败。`HKCU` 是当前用户级。

### 静默启动

自启命令行带 `--minimized`，启动后只隐藏主窗口、**托盘图标照常出现**。
判据是**只看参数不看窗口**：托盘/桌宠窗口也走同一个 setup，
按窗口名过滤会出现"自启后连图标都没有，完全不知道它在跑"。

### 测试踩的两个坑

**坑 1：读回的注册表值末尾多一个 `\0`。**
`RegQueryValueExW` 的 `size` 是 in-out 参数（进去是容量，回来是**实际字节数**，
含终止符）。按 `bytes/2 + 1` 分配缓冲区后只 `pop()` 一次会留下多余的 `\0` ——
控制台看不见，但字符串比较失败。修正：`buf.truncate(size/2 - 1)`。

**坑 2：测试之间互相踩。**
这些测试改的是**同一个注册表键**，而 `cargo test` 会把不同测试二进制并行跑，
进程内的 `Mutex` 跨不过去。实测症状：串行 7 全过、并行稳定 1 条失败。
修正：`static OnceLock<Mutex<()>>` 串行化。**判据是默认并行也必须全绿**，
只跑 `--test-threads=1` 是掩盖。

测试会写真实注册表，因此每次都恢复原状（`读写状态必须自洽` 末尾断言
恢复到测试前的状态）。

## 三、token 截断：根因不在 `max_tokens`，在 `num_ctx`

这是本批次最反直觉的一条。

### 现象

用户在 DSH 里看到「已达到输出 token 上限」。第一反应是 `maxTokens` 配小了——
确实是我配的（8192，而同机 ollama provider 用 65536）。

### 但改大 `maxTokens` 完全没用

实测（请求里明确给了 `max_tokens: 65536`）：

| 路径 | completion_tokens | 正文长度 |
|---|---|---|
| `/v1/chat/completions` → Ollama | 4064 | **0 字符** |
| `/v1/messages`（Claude Code） | 4056 | 3787 字符 |
| `/v1/responses`（Codex CLI） | 4053 | **0 字符** |

**卡在 4064 附近，且 `max_tokens` 给多少都没用。**

### 真正的根因链

1. Ollama 的 `num_ctx` 默认只有 **4096**，且 **prompt 与输出共用**这 4096。
2. 三个本地模型**都是推理模型**（都有 `thinking` 字段）。
3. 复杂任务时 thinking 吃光预算：`thinking` 9614 字符、`content` **0 字符**、
   `done_reason: length`。
4. 所以截断的**不是输出，是思考**。

**证伪实验**（直连 Ollama，绕开网关）：

| 参数 | eval_count | content | thinking |
|---|---|---|---|
| `num_predict=40000`（默认 num_ctx） | 4064 | 0 | 2922+ |
| `num_predict=65536, num_ctx=8192` | **8160** | **12309 字符** | 2922 |

⇒ 瓶颈是 `num_ctx`，不是 `num_predict`。

### 网关的第二层问题：`options` 被丢弃

`to_ollama_body` 只映射了 temperature / top_p / max_tokens / stop 四个已知字段，
**客户端给的 `options.num_ctx` 直接被丢掉**。于是即便客户端知道要发也发不出去。

修完后 `/v1/chat/completions` 实测：`completion_tokens` 从 4064 → **5608**，
正文 7614 字符。

顺带修了一个方向相反的坑：入站解析里 `options.num_predict` 的优先级
**高于** `max_tokens`，导致显式的 `max_tokens` 被静默忽略。交叉测试
`ollama_options_不得覆盖显式的_max_tokens` 钉住这个优先级。

### 为什么 `num_ctx` 必须网关侧注入

`num_ctx` 是 Ollama 专属旋钮，**Anthropic 与 Responses 协议里没有这个字段**——
Claude Code 与 Codex CLI 不可能知道要发它。所以要么客户端侧改（不可能），
要么网关侧按配置注入。已加 `AppConfig::ollama_options`
（`OllamaOptionsConfig`，默认 `num_ctx = 32768`）。

> 注意这与 `Dialect` **正交**：`Dialect` 决定"请求转成什么格式发给上游"，
> `ollama_options` 决定"发给上游后额外带哪些 Ollama 旋钮"。

## 四、缓存命中数被丢弃

`usage_from_ollama` 写的是 `..Default::default()`，
把 Ollama 返回的 `prompt_eval_cached_count` **整个吞掉**。

表现不是"少个数字"，而是**缓存命中率恒为 0**——本地模型的多轮对话
全靠 prompt 缓存提速，命中率掉到 0 意味着每轮重算全部历史。

**端到端验证**（同一 prompt 连发两轮）：

```
第一轮: usage 无 prompt_tokens_details        ← 正确，首次请求确实没命中
第二轮: prompt_tokens_details: {cached_tokens: 1628}
直连 Ollama 对照: prompt_eval_cached_count = 1628   ← 完全一致
```

口径：`cache_read_tokens` 是**已包含在** `prompt_tokens` 里的部分，
所以 `total_tokens` 不能把它再加一次（有断言守住）。

## 五、新增 `Dialect::Responses`

### 为什么需要

Codex CLI 只认 `/v1/responses`。而 `Dialect` 原本只有
OpenAI / Anthropic / Gemini / Ollama 四种 ⇒ **只有 Chat Completions 的供应商
能被 Codex CLI 使用**。

### Responses ≠ Chat Completions 换个字段名

| | Chat Completions | Responses |
|---|---|---|
| 消息 | `messages: [{role, content:"文本"}]` | `input: [{role, content:[{type,text}]}]` |
| 工具 | `tools: [{type:"function", function:{…}}]` | `tools: [{type:"function", name, parameters}]`（**扁了一层**） |
| 输出上限 | `max_tokens` | `max_output_tokens` |
| 响应 | `choices[0].message.content` | `output[]` 嵌套 `content[]` |
| system | messages 里一条 | 顶层 `instructions` |

把 `input` 误当 `messages` 发过去，上游会 400 或静默返回空。

### 一条容易漏的映射

`status: "incomplete"` + `incomplete_details.reason == "max_output_tokens"`
**必须映射成 `length`**。当成 `stop` 的话，客户端以为拿到了完整答案，
内容却是残缺的——这是最难发现的一类静默错误。

### 接入的六个点

`domain/provider.rs`（枚举 + `client_path`）、`proxy/upstream.rs`
（URL / 请求体 / 响应解析 / 流式 / 成功判定 / 透传路径放行）、
`model_catalog.rs`（模型发现 / 鉴权头 / 路径归一化）、
`media.rs`、`db/repo.rs`、`commands.rs`、前端 `api.ts`。

其中「自定义上游路径」原本只放行 `Dialect::OpenAI`，已一并放行 `Responses`
（它是 OpenAI 系，拦掉会让该特性对 Responses 方言失效）。

### 客户端入口 ≠ 上游方言

这两件事**正交**，可以任意组合：Codex CLI 完全可以打到一个 Anthropic 上游
（走 `/v1/messages`）。新增方言解决的是"网关发往上游的格式"，
不影响"客户端怎么问网关"。

## 失败轨迹（保留作为证据）

1. **`RegSetValueExW` 的 `reserved` 是 `u32` 不是指针** — 写成
   `std::ptr::null_mut()` 报类型不匹配。
2. **`RegQueryValueExW` 的 `size` 是 in-out** — 只 pop 一次尾零会残留 `\0`。
3. **假设错了三次**：以为 `tools` 是 `Vec<ToolDef>`（实际 `Option<JsonValue>`）、
   `Message.content` 是 `String`（实际 `Content` 枚举）、
   `Message`/`ChatRequest` 实现了 `Default`（实际都没有）。
   ⇒ 写测试辅助函数前**必须先读结构体定义**。
4. **批量插入 match 分支插坏了括号** — 在 `if` 前插 `} else` 留了多余的 `if`，
   报 `unclosed delimiter`。批量文本插入后必须立刻 `cargo check`。

## 六、供应商页工具栏按钮折行

### 现象

三个按钮（刷新列表 / 刷新定价 / ＋添加供应商）折成两行，「添加供应商」
被挤到第二行左侧，右侧留下大片空档（用户截图）。

### 根因

工具栏是 `display: flex`，右侧按钮组用了通用的 `.row`（`flex-wrap: wrap`）。
左侧标题那句「统一管理服务与模型… 定价上次刷新：…（更新 0 个，跳过手工价 0 个）」
很长，把按钮组挤到不足三个按钮的宽度，`wrap` 于是生效。

### 修法

给工具栏的按钮组单独一条 `flex-wrap: nowrap` + `flex-shrink: 0`，
窄屏媒体查询里再放开 `wrap`（375px 宽屏下 nowrap 会把按钮挤出屏幕）。

### 实测对照（左侧导航 420px，工具栏净宽 = 视口 − 420）

| 净宽（视口） | 原版 | 修复后 |
|---|---|---|
| 420（840） | **2 行**，按钮组 288px | 1 行，298px |
| 400（820） | **2 行**，按钮组 278px | 1 行，298px |

### 走过的弯路（保留作为证据）

第一次修法是给**左侧标题块**加 `min-width: 0` + `overflow: hidden`，
理由是「让标题可压缩」。逐条注违规自检打脸：

| 删掉的规则 | 结果 |
|---|---|
| `.row { flex-wrap: nowrap }` | **立刻折成 2 行，红** |
| 标题块的 `min-width: 0` | 仍然 1 行，绿 |

⇒ **真正起作用的只有 `nowrap`**，标题侧那组是冗余的。已把它删掉，
免得后人以为它在起作用、改坏了也不会红。

教训：**「看起来对」和「实际起作用」是两件事**，必须逐条注违规验证，
否则会把一个无关规则当成修复留着。

### 断言

`ui-smoke.cjs` 扫净宽区间 `[1080 … 400]`，断言：

- 按钮组行数 == 1
- 按钮组宽度 >= 290px（防「不折行但被压扁」这种变相折叠）

已做注违规自检：删掉唯一有效规则后测试红，并精确报出
`工具栏按钮在净宽 420px（视口 840）下折成 2 行`。
