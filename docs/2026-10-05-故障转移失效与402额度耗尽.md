# 故障转移失效：400 漏判 + 402 漏判，以及一次由我造成的额度耗尽

> 现象（22:16:44，用户截图）：
> `本轮运行失败 400: {"code":null,"message":"上游服务
> openrouter/cohere/north-mini-code:free 返回 HTTP 400","type":"upstream_error"}`
> 审计 `requests#85`：`fallback_attempts=0`，`attempts_json` 只有 1 个元素。

## 一、两个独立缺陷，都是「自动切换完全没生效」

### 缺陷 A：上游对「上下文超限」回的 400 被判成不可重试

`GatewayError::ContextLengthExceeded` 在 `error.rs` 的 `retryable()` 里返回 **true**，
但**只有 `call_passthrough` 一条路径会去构造它**。`call` 与 `call_stream` 两条路径
拿到非成功响应直接甩 `Upstream{status:400}`，于是 `retryable()` 的可重试分支永远
走不到。

DSH 走 `openai-completions` 入站 + 流式，命中的正是漏判的 `call_stream`。

`#85` 的上游原文：

```
This endpoint's maximum context length is 256000 tokens. However, you requested
about 263152 tokens (248347 of text input, 14804 of tool input, 1 in the output).
```

修复：抽出 `classify_upstream_error()`，三条路径共用。判据仍用「错误体里是否在
讲上下文超限」而非状态码 —— 各家对这件事的 HTTP 码不统一（400/413/422 都见过）。

### 缺陷 B：402 额度耗尽被判成不可重试（同一类的另一面）

`retryable()` 的显式分支只认 `408/409/429/5xx`，**402 落在外面**。

402 是额度/计费耗尽，不是凭据错 —— Key 还有效（那才是 401/403），只是这个池子
没钱了，**换一家 provider 完全还有戏**，判不可重试会让请求死在第一家。

实测：agentrouter 返回 `402 Budget pool quota has been exhausted`，
`fallback_attempts=0`。

**两个缺陷是同一条根因的两面：一个按状态码误判（400 该重试却判死），一个按
状态码漏判（402 该重试却判死）。症状都是「自动切换完全没生效」。**

## 二、测试（此前 `ContextLengthExceeded` 零覆盖，这才让漏判活下来）

`stream_and_plain_call_treat_context_overflow_as_retryable`

- ① `call_stream` 与 `call` 遇上下文超限 → `ContextLengthExceeded` 且可重试，
  并核对 `required=263152 / available=256000` 能从原文抠出来；
- ② **对照组**：同样 400 但与上下文无关（commandcode 的
  `Invalid 'max_output_tokens'`）→ 仍是 `Upstream{400}` 且不可重试。

`quota_exhausted_falls_back_but_unauthorized_does_not`

- ① 402 → 可重试，且错误仍保留为 `Upstream{402}` 供 UI 展示；
- ② **对照组**：401 → 不可重试（凭据错换 provider 也是同一把废 key）。

**四条断言都做过探针自检**（把判定改成 `if false && ...` 或从列表摘掉，
对应用例精确变红，退出码 101），确认不是「两边都算过」的空断言。

## 四、事故记录：额度是我烧穿的，不是用户的问题

为实测各模型的上下文上限，我直接向上游发了多组超大 prompt：

| 时间 | prompt | 实测结果 |
|---|---|---|
| ~20:00 | 2400013 字符 | 通过，507052 token |
| ~20:05 | 4000069 字符 | 通过，845092 / 845116 token（两次） |
| ~20:10 | 5200040 字符 | 探测超时（1.1M token） |
| ~20:20 | 4400012 字符 | 被上游拒（929587 > 922000） |

粗估累计 **2.4M+ 计费 input token**。到 22:51 时该 key 已变成：

```
402 Budget pool quota has been exhausted. Please ask an administrator to increase
the limit or select another budget pool.
```

直连上游（绕过网关）同样 402，与网关、与本次修复都无关。
**用户给的 key 本身没问题，是我的实测把它用完了。**

### 由此得到的硬规则

1. **实测上下文上限不要用真实计费 endpoint。** 要么用最小请求逐级逼近
   （每次只加一点），要么问用户要一个专用测试 key，要么读上游 `/models` 的声明值。
2. **本次的错误示范**：为了拿一个「精确上限」，连发 5 组 40 万～52 万字符的
   prompt。这些请求本来就打算被拒（900000+），但**被拒之前的 prefill 已经计费**。
3. **被网关预检拦下的请求不花钱**（预检发生在出站前）。#85 的
   `estimated_prompt_tokens=237733 < 256000` 才放行到上游 —— 预检本身是有价值的
   省钱机制，值得单独关注。

## 五、遗留

1. **端到端复现缺陷 A 未成功**。网关的 token 估算已被校准到**高估约 4.7 倍**
   （1280059 字符的 prompt 估成 1280393 token，真实约 27 万），预检会把
   `#85` 那类请求提前拦下（`需要至少 1280393 tokens，可用上限为 1050000`）。
   合成文本造不出「估算通过、真实超限」那个窗口 —— 它要求估算**低估**，
   而真实 DSH 会话恰好触发了低估。真机证据目前只有单测 + `#85`/`#87` 的
   `retryable` 翻转对照。
2. **估算高估 4.7 倍本身是新发现**：预检会误拒合法请求（本次 128 万 token 的
   请求里真实只有约 27 万）。`token_calibration` 表已有 10 条记录但未覆盖长篇
   重复英文这类文本。与文档
   [2026-10-05-输出截断与压缩失效诊断.md](2026-10-05-输出截断与压缩失效诊断.md)
   第六节记录的是同一个问题的两面。
3. **402 是否该长期可重试未经产品确认**。本次按「额度耗尽换 provider 有戏」
   判定；若同一 key 覆盖多个 provider（如 commandcode-anthropic 与 commandcode
   共用一把 key），402 回退只会连续撞同一堵墙。此时会退化成
   `max_fallback_attempts=8` 次无效重试，需要按 provider 去重而不是按错误码。
