### 1.2 关键结论：tauri 在本机 windows-gnu 下无法编译，必须用 MSVC

走 windows-gnu 时链接器问题已全部解决（dlltool 找不到 → 换 llvm-mingw 的 dlltool；
换进去后 DLL 缺失 → 把 llvm-mingw 加 PATH；`-lkernel32 / crtend.o` 找不到 →
`-C link-self-contained=yes`；链接器被 clang 抢走 → 调 PATH 顺序），
但 **`tauri` 的 build script 必崩**：

```
error: failed to run custom build command for `tauri v2.11.5`
  process didn't exit successfully: ...build-script-build (exit code: 0xc0000005, STATUS_ACCESS_VIOLATION)
```

用插桩法定位（把 tauri 源码复制到临时目录、在 `build.rs` 关键节点写文件探针，
再用 `[patch.crates-io]` 把项目指向这份探针版）：

| 实验 | 结果 |
| --- | --- |
| 探针版 tauri 作为**根包**单独构建 | build script **完整跑通**，探针记录到 `main:enter → has_feature → out_dir → before_global_scripts` |
| 项目指向探针版 tauri | **仍然崩，且探针文件根本没被创建** ⇒ 崩在 `main()` 之前（进程初始化阶段） |
| 我们自己的 `build.rs`（调用 `tauri_build::build()`） | **执行成功**——只有 tauri 那个脚本崩 |
| 干净 crate，只依赖 `tauri = { version = "2", features = [...] }`，`src/lib.rs` 只有 `pub fn noop()` | 复现同样的 `0xc0000005`，且解析到的是**更新的 tauri 2.12.1** |
| 同上但 `default-features = false` | 同样崩 ⇒ 与特性集无关 |
| 同上但改用 `cargo build`（而非 `cargo check`） | 同样崩 ⇒ 与命令模式无关 |
| `-C link-arg=-Wl,--stack,33554432` | `llvm-readobj --file-headers` 确认 `SizeOfStackReserve: 33554432` 已生效，**仍然崩** ⇒ 不是栈溢出 |
| `-C target-feature=+crt-static` | 仍然崩 |
| Rust 1.88 / 1.90 / 1.93 三个版本 | 全部同样崩（1.88 因依赖要求 rustc ≥ 1.90 无法构建到 tauri） |
| 同目录其余 8 个 build script | 逐个运行全部正常退出 |
| `llvm-readobj --coff-imports` 对比可运行/崩溃的二进制 | 导入表等价，无缺失 DLL |

**唯一规律**：同一份 tauri 源码，作为**根包**构建时 build script 跑通；
作为**依赖**编译时必定崩。这是 rustc 1.99 + `x86_64-pc-windows-gnu`
在「依赖的 build script」链接路径上的缺陷，与本仓库代码无关。

装上 VS Build Tools（MSVC 14.44.35207 + Windows SDK 10.0.22621.0）并切到
`stable-x86_64-pc-windows-msvc` 后，**同一个 build script 一次跑通**。

`scripts/cargo-env.ps1` 已改写为 MSVC 版本：把 `VC\Tools\MSVC\<ver>\bin\Hostx64\x64`
与 SDK 的 `bin / Lib / um / ucrt` 加进 PATH（**前置**，MSVC 工具链不需要
`-C link-self-contained`，那是 GNU 专用）。脚本注释为纯 ASCII —— 无 BOM 的 UTF-8
脚本在中文 Windows 上会按 GBK 解析，中文注释会打乱语句边界。

### 2.6 edgeJev 在**网关自己的问法**下的真实表现（这一条改了设计）

§2.2 是手工构造三种问法试出来的。编译器装好后，
`tests/live_local_models.rs` 用**网关代码实际发出的问法**重测了一次，
结果和 §2.2 不一样——**以这一节为准**。

五条样本，生产阈值（confidence ≥ 0.35 且 margin ≥ 0.25），分类器强制走 Jev：

| 样本 | Jev 分布 | confidence | 结果 | 启发式 | 对错 |
| --- | --- | --- | --- | --- | --- |
| 把变量名 x 改成 userName | simple 0.898 | 0.641 | **采纳 simple** | simple | ✅ |
| 写一个快速排序算法 | — | 0.117 | 弃权 → simple | simple | ✅ |
| 帮我设计一个分布式限流器… | — | 0.005 | 弃权 → reasoning | reasoning | ✅ |
| **线上服务 500 白屏，帮我定位根因** | **simple 0.936** | **0.747** | **采纳 simple** | **reasoning** | ❌ |
| 你好 | simple 0.923 | 0.707 | 采纳 simple | simple | ✅ |

**采纳 3/5，其中 1 条是自信地判错。**

关键不在「它会不会弃权」，而在第 4 行：edgeJev 对「线上排查」给出 0.747 的高置信度
和 0.936 的分布，**而启发式因为命中「定位」「根因」判成 reasoning，是对的**。
原来的实现里 `Some("simple")` 只在 `heuristic.complexity >= 60` 时才保留推理，
这条样本算出 55 —— 刚好从缝里漏过去，被 Jev 降级成了 simple。

也就是说：**光靠 confidence/margin 双阈值挡不住这类错误。**
模型可以又自信又错，阈值只衡量它有多确定，不衡量它有多对。

#### 因此改了设计

`REASONING_THRESHOLD = 50` 提为单点常量，`classify_by_heuristic` 的分档边界和
Jev 的降级否决**同源**：只要启发式越过 50（也就是它自己会判 Reasoning），
Jev 的「简单」结论就不许降级它。

- 改前：Jev 高置信度地说「简单」→ 可以覆盖启发式 → 第 4 行样本被判错
- 改后：同一输入下启发式 55 ≥ 50 → 降级被否决 → 判 reasoning ✅

两条回归锁住这个行为（`tests/intellect.rs`）：

| 用例 | 作用 |
| --- | --- |
| `jev_高置信度_说简单也不许降级启发式的推理判定` | 用**实测到的那个响应**（simple 0.936 / conf 0.747）驱动。先断言「Jev 确实被采纳」再断言「降级被否决」——少了前半句就是空断言 |
| `jev_说简单且启发式本来就不认为复杂时才允许降级` | 对照组。启发式本来就在阈值下时，Jev 的「简单」**应当**被采纳 |

### 2.7 提示词预优化为什么必须拆成两步

Jev 走的是 scoring pass（§2.2 实测 `output_tokens` 恒为 0），**它产不出任何文本**。
所以「预优化提示词」只能是：

1. Jev 回答「这条提示词是不是含糊到值得改写」——用 `clarity` noul，**越低越含糊**；
2. 判为需要时，另调一次**小模型**做改写，改写结果替换发给上游的最后一条 user 消息。

这两步的失败模式完全不同，所以拆开：Jev 挂掉只是判定不出（回落启发式），
而改写模型挂掉或改坏，是会**直接污染发给上游的提示词**的。

风险清单与挡法（详见 `src/intellect/refine.rs` 模块注释与 §4.2）：

| 风险 | 挡法 |
| --- | --- |
| 改写模型超时 / 报错 | 用原文，绝不阻断请求 |
| 改写把提示词膨胀十倍 | 超 `max_chars` 直接判失败 |
| 模型返回「好的，这是改写后的请求：…」 | 剥掉常见包装前缀 |
| 模型返回空串 / 只有标点 | 判失败 |
| 长提示词被压成一句话 | 缩水超过 4 倍判失败 |
| 反复改写 | 每请求最多 1 次，**不重试** |

**不重试**是硬约束：一次失败就用原文；重试会让延迟翻倍，而且第二次改写的输入
已经是改写结果，改两遍的结果无法预测。

| 拉起用户没要求的东西 | `enabled` 默认 false，且路径必须显式填 | `默认配置下自动拉起是关闭的`、`未启用时拒绝拉起且不碰文件系统` |
| 猜错路径启动陌生程序 | 只用用户填的路径，一个字都不猜 | `路径不存在时拒绝`、`配置无效时返回拒绝并写明原因` |
| 重复拉起导致端口冲突 | 先探 `/health` + 进程句柄守重 | `端点已在响应时完全不启动`、`探活路径是_health_不是_systemone` |
| 杀掉用户自己起的服务 | 只停自己拉起的 | `没拉起过时停止返回_false` |

探活只打 `/health` 且**只打一次**（用计数器断言），不探 `/v1/systemone`——
后者会真跑一次推理，而这步每条请求都要走。

命令行参数对着本机 `edgejev serve --help` 的实测输出拼：

```
usage: edgejev serve [-h] --model MODEL [--host HOST] [--port PORT]
                     [--api-key API_KEY] [--threads THREADS] [--provider PROVIDER]
```

`--host` 写死 `127.0.0.1`（端点无鉴权，绝不能绑 `0.0.0.0`），
`--provider` 写死 `cpu`（延迟敏感路径上不留自动探测的不确定性），
**不传 `--api-key`**（本仓库没有决策端点鉴权配置，传空值反而让某些版本解析失败）。

`本机_edgejev_的路径约定与命令构造一致` 这条直接用用户给的真实路径
（`.venv-runtime\Scripts\edgejev.exe` + `jev-int8`）跑 `preflight`，
确认能通过校验 —— 但**没有真的 spawn 过**（那是不可逆副作用，需要用户自己开开关）。

### 4.7 校准报告（`tests/calibrate.rs`，22 条全过）

15 条测统计（喂构造好的 `SampleOutcome`），7 条端到端（起 mock 决策端点跑真实 `calibrate()`）。

三类样本分开测，因为它们对应三种完全不同的动作：

| 情形 | 期望结论 | 用例 |
| --- | --- | --- |
| 净收益为正 | 可以放宽阈值 | `jev_采纳后确实更好时净收益为正` |
| 净收益为负 | 加否决规则或关掉 | `jev_自信判错时净收益为负并点名错法` |
| 全弃权 | 阈值太严 | `jev_全被弃权时明确说它不参与决策` |

另有**对照用例**：`jev_判对而启发式判错计入净收益正方向` 与
`jev_自信判错时净收益为负` 分开统计 —— 合并成一个「总正确率」会让报告失去意义。

还有两条容易被写错的：

- `净收益为正时仍然要报出错判的置信度` —— 净收益为正不代表没有错判，
  措辞不能只报喜，否则用户会以为可以放心放宽阈值。
- `矩阵每一行的和等于该类别样本总数` + `混淆矩阵按真实类别分行` 里的
  **对角线之和 == 采纳后正确数**：矩阵和计数是两条独立路径，对不上就说明其中一处统计错了。

端到端那 7 条守的是「统计逻辑和真跑分类对得上」，其中两条是失败路径：
`端到端_没有决策端点时全部弃权而不是报错`、`端到端_决策端点不可达时报告仍然产出` ——
校准工具在端点挂了的时候必须仍然给出报告（全弃权），那本身就是有用信息。

#### 这一批抓到的三个真问题

**① 预优化对所有真实供应商都 404（产品 bug，已修）**

现象：真机验收里改写调用回 `HTTP 404`，`X-Route-Refined=0`，note 写「改写端点返回 HTTP 404」。
从界面看只是「改写没生效」，完全指不到 URL 拼错。

根因：`refine.rs` 里写死了 `format!("{}/v1/chat/completions", base_url)`，
而供应商的 `base_url` **本来就带版本前缀**——Ollama 是 `…:11434/v1`、
OpenRouter 是 `…/api/v1`、Anthropic 是 `…/v1`。拼出来是 `/v1/v1/chat/completions`。
修法与 `proxy::upstream` 的 `append_url_path` 对齐：**只追加路径段**。

**单元测试为什么没抓到**：mock 上游的 base_url 写的是 `http://127.0.0.1:PORT`，
**不带** `/v1`，于是硬编码版本恰好拼对了。这正是「mock 形状必须与真实一致」
的又一条实证——已经因为 mock 只挂 POST 踩过一次，这次是 base_url 形状踩的。
新增 5 条回归测试，其中 `带_v1_前缀的真实形状上游能收到改写请求` 是端到端的。

**② 默认上游超时对本机本地模型必然超时（配置 bug，已修）**

现象：真网关打真 Ollama，一条「容量估算与一致性证明」的回答拿到 `504`，
实测 **120.1 秒**被网关掐断。

排查过程（每一步都排除了一个变量）：

| 步骤 | 结果 |
| --- | --- |
| PowerShell 直连 Ollama `/api/chat` | **13–24 秒** —— 上游本身没问题 |
| PowerShell 直连 Ollama `/v1/chat/completions` | 21 秒 —— 协议面也没问题 |
| reqwest 直连 Ollama（不经网关） | **271 秒** —— 差 11 倍！ |
| 短请求（要求「说一个字」） | 12–14 秒，但 `completion_tokens≈190` |

最后一行是关键：这台机器上 `qwen3.8:27b-q4_K_M` 是 **CPU 推理，约 1.1 秒/token**。
「说一个字」也要 12 秒，因为它是 thinking 模型，预算先烧在思维链上
（`content` 空、`eval_count=190`）。要求「容量估算与一致性证明」就是 240+ token → 271 秒。

原默认 `upstream_timeout_secs = 120` 对本项目主打的**本地模型场景是必然超时**：
一问就 504，功能等于不可用。已改为 **600 秒**。
设长只影响「上游真挂了要等更久才报错」，设短会让慢但正常的模型被误判成故障。

> 这条也说明：**默认值不能拍脑袋**。120 秒对云端模型是对的，对本机 CPU 大模型是错的。

**③ 「跳过」被 cargo 记成 ok，差点自己被骗过去**

第一轮跑出来 6 passed / 1 failed，其中两条显示 ok —— 但 `--nocapture` 里有
「跳过：没有能对话的模型」。也就是说它们**什么都没验**却算通过。

两个原因叠加：

- `pick_ollama_model` 用「`content` 非空」当判据，而 thinking 模型会把
  `num_predict` 预算烧在思维链上，`content` 天然为空 → 误判「不能对话」；
- 跳过用 `eprintln!` + `return`，cargo 记 **ok**。

已改成两段式：**只有「后端没启动」才跳过；「后端在跑却用不了」必须 panic**。
`require_model()` 就是这条边界的守卫。

| `智能模式开启时含图请求被标为_vision` | 含图 → `X-Route-Intent: vision` + `X-Route-Classifier: rule`（硬规则命中就不问 Jev） |
| `智能模式开启时纯文本请求由启发式判定并回出分类来源` | Jev 端点为空时明确回 `heuristic`，而不是沉默 |
| `启用搜索但后端不可达时请求照常发出且标为_failed` | **搜索失败不阻断**：上游仍被调用一次，头回 `failed` + `0` |
| `不需要联网的请求不会触发搜索` | 没触发检索时连 `X-Route-Search` 都不出现 |
| `搜索命中时结果被注入到上游请求的上下文里` | 断言注入文本**真的进了上游的 messages**，且带可点击来源链接、不含任何凭据 |
| `审计落库时记下了判定与搜索结果` | 审计里留下 `route_intent` / `route_classifier`，没触发检索时 `route_search` 为 null |
| `改写成功后上游收到的是新提示词` | 断言上游收到的最后一条 user 消息**就是改写后的文本**，原文不再出现 |
| `改写关闭时上游收到的是原文` | 对照组。Jev 说要改写但开关关着 → 端点零调用、原文逐字送达 |
| `jev_说清楚时不做改写` | 反向对照。断言 `X-Route-Classifier: jev`，否则「不改写」可能只是因为弃权 |
| `改写端点报错时请求照常走完且提示词未被污染` | 改写 500 → 头回 `0` + 具体原因，上游仍被调用，**原文逐字保留** |
| `没有可用改写目标时明确说明而不是沉默` | 选不出改写模型也要在审计里写原因，否则界面是空白 |
| `审计记录了改写前后的长度` | 审计里能看到「原文多少字 → 新文多少字」，可人工核对改写幅度 |

改写用例里有个**测试设计上必须绕开的坑**：改写端点本身是一个合法的供应商，
如果它的模型也能满足主请求的硬约束，它就会被主路由选中——那样

解决办法是让改写模型的 `supports_tools = false`，而主请求**带工具**：
硬约束会把它从主候选链里剔除，但选改写目标时用的 `RequiredCapabilities::default()`
不要求工具，它仍然能被选中。

### 4.3 端到端逼出来的一个真 bug：响应头里的中文读不出来

`x-route-refine-note` 的值是中文「改写端点返回 HTTP 500」。
测试报「头是空的」，但打印响应头发现它**确实存在**：

```
HDR x-route-refine-note: "\xe6\x94\xb9\xe5\x86\x99\xe7\xab\xaf\xe7\x82\xb9\xe8\xbf\x94\xe5\x9b\x9e HTTP 500"
```

`HeaderValue::from_str` 会放行 0x80–0xFF 的原始字节，所以中文写得进去；
但客户端的 `HeaderValue::to_str()` 遇到非 ASCII 返回 `Err`——
**头「存在」却读不出来**，表现得和没发一样。

第一版修法是「只在 `from_str` 失败时才编码」，结果无效，因为 `from_str` 根本没失败。
改成**无条件**编码：纯 ASCII 原样返回，非 ASCII 转 UTF-8 的 `%XX`。

这类缺陷只有在真发真收的测试里才会暴露，纯函数测试和「头在不在」的断言都发现不了。

#### ① 配置读坏 = 应用彻底打不开（最严重）

实测：`backend = "duckduckgo"`（正确是 `duck_duck_go`）写进 `config.toml` 后启动，
日志停在 `load config failed`，**网关不监听、窗口只剩一个空壳**。
用户既用不了，也没有办法自救。

修法（`config.rs::load_or_init_at`）：解析或校验失败时

1. 把坏文件**挪**成 `config.corrupt-<时间戳>.toml`（挪不是删——用户手改的内容不能丢）；
2. 写一份默认配置回原位（否则下次启动还会反复降级）；
3. **照常启动**，并把「原配置没生效 + 备份在哪」经 `BootState.warning` 透到界面横幅。

刻意不用 `#[serde(other)]` 之类静默兜底：那会把错值悄悄当成别的值（比如 `brave`），
用户看到「换了后端行为怎么变了」比看不到更费解。**降级必须可见且可回滚。**

真机复验：注入同一个错值 → 网关 **1 秒起来**，日志记录降级，坏配置完整保留，
界面顶部横幅完整显示行号、错值、合法值列表、备份文件名（见截图）。

### 4.14 前端真跑补上的三个断言，以及「夹具形状失真」第 N 次

### 4.15 同一个后端有两套字符串，以及一个会骗过你的缓存

#### 设计问题：配置值与展示值不是同一套

加 `bing_cn` 时顺手查了枚举，发现同一个后端有两个字符串：

| 用途 | 由谁产出 | `SearXng` | `DuckDuckGo` |
| --- | --- | --- | --- |
| 配置文件 / 前端下拉 | serde `rename_all="snake_case"` | `sear_xng` | `duck_duck_go` |
| 响应头 / 审计展示 | 手写 `backend_code()` | `searxng` | `duckduckgo` |

两套**都能正常工作**，但用途不同、不可互换：

- 写成展示值 → TOML 解析失败 → **整个应用打不开**（这个坑第一天就踩过）。
- 写成配置值 → 响应头变成 `sear_xng`，只是难读，功能不受影响。

**不对称意味着两种写错的后果差了两个数量级**，所以必须让「会不会写混」变成可失败断言，
而不是靠人记住。

#### 修法：给配置值一个程序化取值

原来没有任何函数能拿到 serde 值 —— 所以「两套会不会被误合并」**无法用测试守住**，
只能靠注释提醒（注释正是最容易在迭代里失效的东西）。

加了 `search::backend_serde_value(&kind)`，从 serde 序列化结果反推，
不再手写第二遍 `snake_case`。手写第二遍就是漂移的开始。

#### 测试可失败性已验证

```rust
// 对照组：展示值不得等于配置值，否则两套字符串会在维护中被误合并，
// 而配置侧会随之解析失败。BingCn 恰好同形，必须显式豁免。
for kind in [SearchBackendKind::SearXng, SearchBackendKind::DuckDuckGo] {
    assert_ne!(backend_code(kind.clone()), backend_serde_value(&kind), ...);
}
```

按纪律**注入了一次真实回归**验证它会失败 ——
把 `backend_code` 的 `searxng` 改成 `sear_xng`：

```
test 后端码_响应头用的必须是展示拼法 ... FAILED
  left: "sear_xng"
 right: "searxng"
test result: FAILED. 41 passed; 1 failed;
```

恢复后 42 passed / 0 failed。**没有这条注入验证，就不知道这个断言是不是永远为真。**

`BingCn` 两套恰好同形（都是 `bing_cn`），所以它看不出差别 —— 那是巧合，
所以对照组里要显式列出它而不是让它默认通过。

#### 踩坑：cargo 的 mtime 缓存会造出「源码已恢复但测试仍红」

恢复文件用 `Move-Item` 从备份移回，**内容是对的**，但 mtime 可能与
上次编译时一致或更早，cargo 判定「没变」→ 复用带回归的 `.rlib` → 测试继续红。

现象极像「恢复没生效」，差点去改代码。判据是：

```
grep 源码确认值已是 searxng  ← 内容正确
cargo test 仍 FAILED          ← 但结果是红的
```

**结论：`cargo test` 的结果不能单独作为证据，源码内容必须一起看**；
注入回归后恢复，务必 touch 一次刷新 mtime：

```powershell
$b = [IO.File]::ReadAllBytes($m); [IO.File]::WriteAllBytes($m, $b)
```

这与「本轮编译退出码必须是判据的一部分」是同一条：复用旧产物会造出假证据。

### 4.16 edgeJev 环境：修好了 venv，但缺的不是 venv

### 4.17 SearXNG 死锁：一个被夹具掩盖了整整两轮的真 bug

用户 2026-10-05 报告：「选择 SearXNG 后端时填写实例地址的功能没有」。
输入框**代码里是有的**（`LocalModels.tsx` 条件渲染），所以第一反应是「是不是旧版本」。

#### 为什么前两轮没发现

`verify:ui` 一直是绿的，而且**真的截到了输入框显示的图**。
因为夹具的 `update_search_settings` **不做任何校验** —— 它直接
`{...search, ...next}` 就返回，而后端 `commands.rs` 在保存前一定会调：

```rust
crate::search::validate(&next.search).map_err(|e| e.to_string())?;
```

这是「夹具形状与真实不一致」的第 N 次，但这次形态是**校验缺失**而不是返回值形状。

#### 真实因果链（这是个死锁，不是「少了个输入框」）

```
用户在下拉选「SearXNG」
  -> onChange 立刻 save({backend:"sear_xng"})，此时 searxng_url 为空
  -> 后端 validate 拒绝：「选择 SearXNG 后端时必须填写实例地址」
  -> settings.backend 不变
  -> 输入框的显隐条件是 settings.backend === "sear_xng"（已保存值）
  -> 输入框永不出现
  -> 用户没法填地址，也就永远保存不了
```

**输入框恰恰是因为「已经保存成功」才该出现，而它自己的出现又是保存成功的前提。**

#### 修法：把「用户当下选了什么」与「已保存什么」分开

```tsx
const [pendingBackend, setPendingBackend] = useState<... | null>(null);
const shownBackend = pendingBackend ?? settings?.backend ?? null;
```

- 输入框显隐用 `shownBackend`（用户意图），**不依赖保存结果**；
- 选 SearXNG 且地址为空时**不提交**，等地址填好再一起提交
  `{ searxng_url, backend: "sear_xng" }`；
- 保存失败时保持 `pendingBackend`，否则用户会看到下拉跳回旧后端、
  输入框消失，且不知道刚才输入去哪了。

**同类问题一并修了**：`backend_needs_key` 也是**已保存**配置的回传值，
选 Tavily/Brave 时 Key 框要等一次往返才出现。改成按 `shownBackend` 判断。

#### 测试打在哪才算打中

第一版断言写成「等保存成功 -> 输入框出现」，结果**把 bug 当成了通过条件**。
正确的落点是「保存**之前**输入框就出现」：

```js
await backendSelect.selectOption("sear_xng");
const searxInput = page.getByPlaceholder("http://127.0.0.1:8888");
await searxInput.waitFor({ timeout: 5000 });   // <- 这里
```

已注入原始 bug（把条件改回 `settings.backend`）验证：
`locator.waitFor: Timeout 5000ms exceeded` ✅。

我还先写了一版「不得提交 SearXNG（没发 IPC）」的断言，注入回归后发现
**它也测不出问题** —— 因为去掉守卫后同样不会发 IPC。已删掉：
断言必须打在用户可感知的不变量上，不是实现细节。

#### 夹具补上校验（否则下次还会漏）

```js
if (next.backend === "sear_xng") {
  const url = ("searxng_url" in next ? next.searxng_url : cfg.search.searxng_url) ?? "";
  if (!String(url).trim()) throw "选择 SearXNG 后端时必须填写实例地址";
}
```

#### 顺带修掉的功能缺口：自动拉起不支持 python + 脚本

`tests/autostart.rs` 原本把 Jev 路径写死在 C 盘，而本机在 2026-10-05
搬到了 E 盘并改用 `python.exe start_jev.py` —— 测试以
「可执行文件不存在」失败，看起来像代码坏了，其实是**环境变了**。

改成「先找到再断言」，同时暴露了一个真缺口：`AutoStartConfig` 只有
`exe_path` 一个字段，表达不了 `python.exe start_jev.py`，而
`command_args` 还会无条件加 `serve` 子命令 —— 脚本的 argparse 直接从
