# 2026-10-05 「已达到 output token 上限」根因诊断

> 现象：DSH 会话跑到 66 轮 / 270 步后，界面弹出「已达到 output token 上限 回答被截断」，
> 提示让用户发「继续」接着输出。
> 结论：**提示是误导。真因是上下文压缩从一开始就没生效，上游按上下文超限处理，
> 与 `max_tokens` 无关。**

## 一、证据链

### 1. 网关侧（`%LOCALAPPDATA%\llm-gateway\gateway.db` 的 `requests` 表）

截断发生在 **18:15:40**，与截图同一分钟：

| id | 时间 | requested | routed | status | prompt_tokens | completion_tokens | latency |
|---|---|---|---|---|---|---|---|
| 81 | 18:15:40 | `auto` | `openrouter/dots-studio/dots-3-note-preview:free` | 200 | **271576** | **1** | 20.3s |
| 80 | 18:05:36 | `auto` | （未路由） | 400 | 0 | 0 | 2.5s |

id=80 的上游报错原文：

```
This endpoint's maximum context length is 256000 tokens. However, you requested
about 261465 tokens (246660 of text input, 14804 of tool input, 1 in the output).
```

id=81 更隐蔽：**HTTP 200，却只吐 1 个 token 就 `finish_reason=length`**。
DSH 把 `length` 翻译成「已达到 output token 上限」，所以用户看到的是输出上限问题。

**上下文 26 万 token 打爆了免费 endpoint 的 256000 上限，输出空间被挤成 1。**

### 2. DSH 侧（`%USERPROFILE%\.dsh-beta\storages\session_projcache\sessions\session-abc660e5-*.json`）

同一会话的投影里：

```json
"contextPressure": { "surfaceTokens": 181393, "contextWindow": 131072, "pressureTokens": 0 }
"modelSelection":  { "lastUsed": { "provider": "llmgw", "model": "auto" } }
```

`surfaceTokens` 181393 已经**超过**声明的 `contextWindow` 131072，
而 `pressureTokens` 恒为 **0** ⇒ **压缩一次都没触发过**。

### 3. 机制：`dsh-compaction-basic/lib/index.js`

阈值公式（:124-132）：

```js
messageBudgetTokens = contextWindow - reservedCompletionTokens;   // 131072 - 65536 = 65536 ✓
pressureBudgetTokens = messageBudgetTokens - policy.headroomTokens;
if (pressureBudgetTokens <= 0) throw new TargetPressureConfigError(...);   // ← 这里
thresholdTokens = Math.floor(Math.min(contextWindow * 0.8, pressureBudgetTokens));
```

`headroomTokens` 默认 **65536**（:63），于是
`pressureBudget = 65536 - 65536 = 0` ⇒ **抛错**。

抛错后被 `agent/pre-step` 的 catch 吞掉（:843-850）：

```js
} catch (error) {
    if (error instanceof TargetPressureConfigError) {
        if (this.warnedPressureConfigTargets.has(error.targetKey)) return next();
        this.warnedPressureConfigTargets.add(error.targetKey);
    }
    ctx.logger.warn(`step compaction failed: ${message}; continuing the turn`);
}
return next();
```

**每个 target 只 warn 一次，然后当作什么都没发生继续跑。**
UI 上完全无感，只有宿主日志里一条 warn。

### 4. 配置漏项

`%USERPROFILE%\.dsh-beta\profiles\desktop\cordis.patch.yml` 的 `modelPolicies`
只覆盖了两个 `provider: ollama` 的模型，实际用的是 `llmgw/auto` ⇒ **零命中**：

```yaml
modelPolicies:
  - provider: ollama          # ← 不是 llmgw
    model: gemma4:12b-it-q4_K_M
    headroomTokens: 8192
```

这批策略当初就是为了绕开 `131072 - 65536 - 65536 = 0` 才写的
（同一文件 :110-112 的注释原话：「W-O-B 一旦 <= 0 压缩引擎直接放弃」）。
**后来加 `llmgw` 这个 provider 时没跟着加**，同一个坑踩了第二次。

## 二、第二条链路：`num_ctx` 不足时 Ollama **不报错，静默砍 prompt**

第 1 节的根因是「压缩没触发」。但把 `default_num_ctx` 从 32768 改到 131072 之前，
先量了一组对照 —— 结果比预想的糟：

同一份 200007 字符（约 42K token）的 prompt，直连 Ollama，只改 `num_ctx`：

| num_ctx | `prompt_eval_count` | `done_reason` | 用时 |
|---|---|---|---|
| 32768（旧配置） | **16387** | `length` | 19.6s |
| 131072（新配置） | **42271** | `length` | 151.5s |

**Ollama 在 prompt 超出 `num_ctx` 时不返回错误，而是把 prompt 悄悄截掉
（25884 token 无声消失），然后把 `done_reason` 设成 `length`。**
网关把它映射成 `finish_reason=length`，DSH 再翻译成「已达到 output token 上限」。

⇒ 用户看到的是「输出不够长」，实际发生的是「**一半输入被丢掉了**」。
两组的 `done_reason` 都是 `length` 只是因为 `num_predict=512` 被 thinking 吃光，
与 prompt 无关；`prompt_eval_count` 才是硬数据。

经网关的最终验证（同一份 prompt，`model=gemma4:12b-it-q4_K_M`）：

```
prompt_tokens = 42271          ← 与 131072 直连组逐 token 一致
finish_reason = stop           ← 不再被截断
```

⇒ `default_num_ctx = 131072` 确认已注入出站 body 并生效。


而遍历模型的那一层也只走 `llm-ollama` 的 `insert` 行。
**llmgw 从来不在校验范围内**，所以漏配策略可以一路绿灯通过。
已改为：策略 Map 不再过滤，`ollama` 与 `llmgw` 共用同一条 `checkBudgets()`。

## 六、本次顺带发现、未修的问题

**网关的 token 估算偏高约 4 倍，会误拒合法请求。** 实测：

| 输入 | 网关估算 | 上游真实 |
|---|---|---|
| 200007 字符英文 | ≈160000（按 0.80 tok/字符） | **42271**（0.21 tok/字符） |
| 355000 字符英文 | **284613** | ≈74500 |

355000 字符那次被网关自己的预检拦下：

```json
{"error":{"message":"请求上下文过长：需要至少 284613 tokens，可用上限为 262144 tokens",
          "type":"context_length_exceeded"}}
```

而实际只有约 74K token，远低于 262144 —— **本该放行的请求被拒了**。
`token_calibration` 表已有 10 条校准记录，说明机制在，但显然没覆盖
「长篇重复英文」这类文本。同一偏差在反方向也危险：
DSH 那次 `estimated_prompt_tokens=237733` vs 真实 `prompt_tokens=271576`，
估低 12%，预检放行后被上游拒。

**未修的理由**：改校准算法属于设计改动（`src/proxy/server.rs:2525` 的估算与校准逻辑），
按本仓纪律第 5 条「不许改设计，发现问题先告诉」处理。已记录在此等排期。

## 七、留给下一个人的三条判据

1. **凡是 `resolveCompactSpec` 抛 `TargetPressureConfigError` 的 target，
   压缩就等于不存在**。新增 provider / 模型时，`modelPolicies` 必须同步补一条，
   否则症状是「提示说输出上限、实际是上下文爆了」，指向完全错误的方向。
2. **`contextWindow` 是声明值，不是能力实测值。** 网关虚拟模型 `auto` 会分流到
   上限从 32K 到 256K 不等的各种上游，DSH 侧只有一个统一的 131072。
   这个不匹配本身是下一批（D 批「选得准」）要解决的问题，本次只做了止损。
3. **本地后端（Ollama）在输入超限时静默截断，不报错。** 任何
   `finish_reason=length` / `done_reason=length` 都要先用
   `prompt_eval_count` 核对输入是否被砍过，否则会把「丢了一半输入」误判成
   「输出不够长」——本次就是被这句话误导了整整一轮排查。
